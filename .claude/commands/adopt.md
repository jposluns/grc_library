Run the `adopt` skill defined at [`.claude/skills/adopt/SKILL.md`](../skills/adopt/SKILL.md). Slash-command entry point is `/adopt`; the underlying skill name remains `adopt`. This is the RUN-ONCE onboarding for a fork that adopts this governance-corpus project: it resets any present maintainer working-state to clean adopter baselines (or, when a fresh clone has none, treats it as already clean and creates only the adopter-local state a public versioned consumer requires), settles how the adopter will handle the optional external reference base and private store, strips maintainer-only operational residue, and records the adopter's choices in a committed adoption marker so later resumptions proceed in adopter mode without re-asking. It runs ONLY on a confirmed adopter clone (a fork origin), never on the upstream maintainer repository, and only once (an existing adoption marker short-circuits it). It never touches the corpus, the pinned rules, the tooling, the gates, or the version lineage, which are the product the adopter came for. Execute the onboarding per the seven-step process the skill encodes:

1. **Confirm this is an adopter clone, and that adoption has not already run**: run `python3 .claude/skills/corpus-management/tools/adopt-preflight-guard.py`; it refuses (non-zero) unless the clone classifies as an adopter fork, so the destructive reset cannot proceed on the wrong clone. Also stop if an adoption marker (`.claude/adopt-config.json`) already exists. Confirm the classification with the operator before any reset.
2. **Choose the dependency model**: ask the adopter, recording the choice, whether they will keep their **own external stores** (a reference base and a private operational store beside the clone) or run **self-contained** (in-repo placeholder stubs `/adopt` creates, or clean no-op degradation). Surface both options with consequences; do not pick silently.
3. **Reset any present working-state to clean adopter baselines**: branch on PRESENCE first. A fresh public clone usually has NO maintainer working-state; if absent, treat it as ALREADY CLEAN, reconstruct nothing, and create only the adopter-local state the chosen dependency model needs, deriving each file's SHAPE from the public versioned consumer (a gate, a tool, or a command) that reads it. If present, clear accumulated DATA to empty baselines while preserving the SHAPE each gate validates. Do not reset the corpus, the tooling, the gates, the public change record, or the version surfaces.
4. **Handle the placeholders per the chosen model**: for **own external stores**, record their locations, and optionally bootstrap the adopter's EXTERNAL reference base from the public bibliography [`reference-acquisition-manifest.md`](../skills/corpus-management/registers/reference-acquisition-manifest.md) using the planner `python3 .claude/skills/corpus-management/tools/adopt-bootstrap-ref.py` (the planner reads only bibliographic metadata and never fetches; fetch the freely redistributable sources into the external store yourself, list the licensed ones for lawful manual acquisition, and never redistribute licensed content). For **self-contained**, `/adopt` CREATES the in-repo placeholder stubs the adopter wants: a README-only marker stub per slot, whose first line is the `<!-- SIBLING-PLACEHOLDER: <name> -->` marker the stub-guard gate parses, kept payload-free by that gate. Fetched reference text goes into an EXTERNAL store, never into a declared in-repo stub; a payload-bearing declared stub hard-fails the stub-guard gate.
5. **Strip maintainer-only residue**: remove or neutralize residual maintainer-only operational content (private-store pointers, contact or watermark tokens, maintainer-specific runbook references the corpus and gates do not depend on). Do not touch the pinned rules, the gates, or the corpus.
6. **Record the adoption marker**: write and commit `.claude/adopt-config.json` with the minimal schema (`mode` = `"adopter"`, `adopted_at` = the UTC date, `sibling_choice` = `"own-siblings"` | `"self-contained"`, `adopt_config_version` = `1`). The committed marker is the durable signal the fork is adopted.
7. **Verify and report**: confirm the reset clone still passes the full audit sweep with no external store present (the adopter-clone portability invariant: `.claude/skills/corpus-management/tools/run_all_audits.sh` exits 0), and report what was reset, the dependency model recorded, and the committed marker location. If a gate fails after the reset, a surface was cleared past its required shape; restore that shape and re-run before declaring the onboarding complete.

Do not run this on a non-adopter clone (step 1 gates it), do not fabricate adopter history (baselines are EMPTY, not invented), and do not re-run on an already-adopted fork without explicit confirmation (the committed marker short-circuits it).

Report back: the confirmed classification, the dependency model chosen, the surfaces reset (and any placeholder or manifest handling), the residue stripped, the committed adoption marker, and the green sweep confirming the reset clone is adopter-ready.
