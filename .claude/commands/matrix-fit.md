Invoke the `matrix-fit` skill defined in this project's pack at [`guardrails/skills/matrix-fit/SKILL.md`](../../guardrails/skills/matrix-fit/SKILL.md). Slash-command entry point is `/matrix-fit`; the underlying skill name remains `matrix-fit` (the descriptive name documents the workflow's purpose, the slash command is the ergonomic verb). This is the cadenced semantic-fit audit of the compliance matrix and per-document framework-alignment tables, catching the gate-blind "valid code, wrong control" class (a control identifier that exists in its catalogue, so gates 48/49/54/58/61 pass it, but is the wrong control for the row's document). It is distinct from the content sweeps (`/validate`, `/validate-pr`) and the trust-recovery suite (`/full-qa`, `/fitness`): those review the corpus or a window of work, this judges control-code semantic fit. Run it after each FR-167 matrix-expansion batch, once at matrix completion, and ad-hoc. Execute the audit per the six-step process the skill encodes:

1. **Establish scope and confirm the reference base**: name the scope (the rows the batch introduced, in FR-167 practice typically one domain section, for the per-batch cadence; the whole mapping surface, the matrix AND the per-document framework-alignment tables, for the completion cadence; or a maintainer-flagged set of rows for the ad-hoc cadence). Confirm `tools/run_all_audits.sh` exits 0 first (a fit pass judges among rows that already pass the existence gates; a red gate is a mechanical defect to fix before the semantic read). Confirm the reference base is available: the in-repo validator modules [`tools/ccm_aicm_reference.py`](../../tools/ccm_aicm_reference.py), [`tools/nist_csf_reference.py`](../../tools/nist_csf_reference.py), [`tools/cobit_iso31000_reference.py`](../../tools/cobit_iso31000_reference.py), and [`tools/iso27001_reference.py`](../../tools/iso27001_reference.py) (gate-validated codes and titles) and the `grc_library_ref` full-text extracts (source control titles; the CSA catalogues under `grc_library_ref/frameworks/CSA/`, the NIST CSF text under `grc_library_ref/standards/NIST/`, the ISO/IEC 27001:2022 Annex A text under `grc_library_ref/standards/ISO/`). The judge reads control TITLES from these, never from memory. Every fit verdict cites the held source's own reference-base `path:line` for the control TITLE it read from the held source located via an EXECUTED `ref-holds` + index read performed in THIS run (never a note, a prior run's record, or memory); a `grc_library_ref` extract's CURRENCY is validated upstream this run, not inferred from the index (P-1.56, from the 2026-08-31 stale-note `grc_library_ref` incident).

2. **Run the advisory pre-filter to generate the worklist**: run `python3 tools/audit-matrix-semantic-fit.py` (with `--matrix-only` or `--source-docs-only` to match the scope; `--docs <paths>` to scope to a batch's documents for the per-batch cadence; `--json` for a triple-family dispatch brief or a run-over-run diff). The tool always exits 0; its output is a recall-oriented worklist of rows that lack any lexical anchor between the document subject and the cited control titles. Treat it as the judge's input-narrowing step, NOT a defect list: a listed row is a candidate to read, a non-listed row is deprioritized (not certified correct). Add any row a maintainer or a prior `/validate` / `/full-qa` note flagged (the loose-supporting-code-on-an-anchored-row case the tool intentionally does not list). A second worklist feeder is the stranded-control-code scan `tools/audit-stranded-matrix-code.py`: a code it confirms is cited on a row but ABSENT from the referenced document is a fit candidate to fold in (a stranded code is not itself a mismatch, per the indicative-citation convention in step 3, but it is judged for fit). For the COMPLETION cadence the worklist is EVERY row of the surface, not the pre-filter's output (the pre-filter and stranded scan narrow only the per-batch and ad-hoc cadences).

3. **Dispatch the semantic-fit judge over the worklist**: dispatch one or more subagents (or read directly for a small worklist) to judge each worklisted row. The brief: read the cited control's TITLE from the reference base for every code on the row, compare it against the row's document subject, and decide fit (`fits` / `mismatch` / `loose-supporting`) with the source title quoted as evidence. The binding rule: judge against the source control TITLE, not a lexical proxy or a remembered meaning (a code that exists and is in-catalogue can still be a mismatch; the source read decides, title first). Every judgement quotes the code, its source title, the row location as `path:line`, and the held source title's own reference-base `path:line` where the title was read this run; a judgement without a quoted source title or its held-source `path:line` is a hypothesis, not a finding (P-1.56). In THIS project this dispatch is the TRIPLE-FAMILY orch-verify panel (one Claude-, one Codex-, one Gemini-family worker, identical brief, verdicts reconciled per the CLAUDE.md standard); "read directly" is the worker's internal execution, never an in-session orchestrator self-QA. The fit rubric, judged against the row's SUBJECT: `fits` = the control's scope covers the row's primary subject; `loose-supporting` = a genuine partial or secondary FIT beside a CORRECT primary anchor (indicative breadth), never the principal control and never standing in for a wrong one; `mismatch` = the code does not fit the subject, INCLUDING a same-family wrong-sibling (right family, wrong specific control), the exact valid-code-wrong-control class this skill catches. Family membership never establishes fit. The title is the primary evidence and the mandatory carrier (every verdict quotes the title and its held-source `path:line`, P-1.56); for a borderline call the title does not settle, the judge MAY additionally quote the control's full specification text with its OWN held-source `path:line` as supplementary grounding, never dropping the title citation. The indicative-citation convention governs literal PRESENCE, not fit: a STRANDED code (cited but absent from the document) is not a defect on that ground alone, but it is still judged for fit and a mis-fit is a `mismatch` whether or not the document reproduces it; route a representative-vs-strict-reproduce boundary case to the pending decision.

4. **Synthesize and apply-time-verify each candidate against the source control title**: the orchestrator re-reads each candidate `mismatch` AND each candidate `loose-supporting` verdict's source title in the reference base before treating it as confirmed (the judge produces research; the orchestrator confirms; a candidate that is really `fits` or `mismatch` on re-read is reclassified, not recorded as retained). A worker false positive (a correct mapping the lexical signal flagged, the dominant case on a clean corpus) is refuted here, not routed. For each confirmed mismatch, identify the correct control by reading candidate titles, so the finding carries both the wrong code and the proposed right code with both titles quoted. When a mismatch is fixed, re-read the paired description cell in the same row for echoes of the old code's meaning.

5. **Triage and route findings**: confirmed mismatches in the current scope are fixed in-window (correct the code, bump the matrix or source document's Version and Date, record the correction in the CHANGELOG-detailed entry). Confirmed mismatches outside the current scope are surfaced to the maintainer with named options (fix-now vs route-to-backlog), not auto-deferred. Findings refuted at apply-time are recorded with the refutation, not routed; findings that dedupe against an existing backlog item are cross-referenced, not duplicated. A confirmed `loose-supporting` verdict (re-verified in step 4 like a mismatch) is never "corrected": it is KEPT as an indicative mapping and RECORDED in the run's detail file (row `path:line`, the code, its source title + held-source `path:line`, the indicative-retention rationale), so only `mismatch` verdicts are fixed or routed.

6. **Record and surface**: surface confirmed findings inline in chat (a `mismatch`: row `path:line`, the wrong code and its source title, the proposed right code and its source title, each title's held-source reference-base `path:line`, fix-in-window vs routed; a retained `loose-supporting`: row `path:line`, the code, its source title and held-source `path:line`, the indicative-retention rationale). Write the run to the project's matrix-fit record location (`grc_library_private/.working/matrix-fit/`) and append a history row; a run with ANY judged `mismatch` OR retained `loose-supporting` verdict also writes a detail file recording each, while a run with neither still gets its history row alone (the proof-of-discipline), with no detail file. The pass terminates when the worklist is judged, the confirmed findings are routed or fixed, and the run is recorded; it is a single advisory pass, not a fix-to-fixed-point loop.

Reject any judge finding that lacks an explicit `path:line` row location, a quoted source control title, AND the title's held-source reference-base `path:line`. A judgement without quoted evidence is a hypothesis, not a finding; re-dispatch with a re-emphasized evidence requirement before synthesizing.

`matrix-fit` does NOT replace the existence gates 48/49/54/58/61 (which run on every PR); it is the semantic layer on top of them. A row must pass the gates first; this skill judges fit among rows that already pass. Passing the gates says nothing about fit.

Report back: the scope and mechanical baseline, the worklist the pre-filter produced, the judge's findings (a `mismatch` per-finding: row `path:line`, wrong code + source title, proposed right code + source title, each title's held-source reference-base `path:line`; a retained `loose-supporting`: row `path:line`, the code, its source title + held-source `path:line`, the indicative-retention rationale), the apply-time verification outcomes (confirmed vs refuted), the fixes applied in-window and the findings routed, and the path to the run record.
