## 1. Purpose

This specification defines the GRC Documentation Library's automated audit programme: the set of machine-checked rules that gate every change to the library, the mechanisms by which the rules are enforced, the surfaces on which they run, and the conditions under which gates are added, modified, or retired.

The audit programme is the library's primary defence against the failure modes catalogued in [`governance/specification-citation-verification.md`](../../../../governance/specification-citation-verification.md) §5: drift, contradiction, mis-attribution, stale references, and silent regressions in document structure, naming, and cross-linkage. Where the Citation Verification Specification governs *what is true about the world* (publisher metadata about external standards), this specification governs *what is internally consistent about the library itself*.

## 2. Scope

### 2.1 In scope

- The audit gates currently wired into the audit-programme (see §6 for the canonical inventory and current count).
- The three enforcement surfaces (CI workflow, local audit runner, pre-commit hook).
- The doctrinal rules for adding, modifying, scoping, and retiring gates (see §9, §10).
- The relationship between the audit programme and the Citation Verification Specification (see §11).

- Manual quality reviews (governed by [`governance/procedure-library-quality-and-review-cadence.md`](../../../../governance/procedure-library-quality-and-review-cadence.md)).

## 3. Design principles

The audit programme rests on five principles:

1. **Determinism over heuristic**. Every gate produces a deterministic pass/fail outcome from the inputs it reads. No gate depends on network access or third-party services for its findings. For most gates the inputs are the repository's files alone; the gates named here read more. First, the date-sensitive gates compare a repository-recorded date field against the current date (per-document date staleness and review cadence, citation and tooling currency and freshness, plus the advisory daily-changelog-rollup check). Three of them, the review cadence, citation verification freshness and tooling provenance freshness audits, take the current date by default from Python's `date.today()`, which is the local date, not the UTC date, so their results also depend on the time zone setting and, near midnight, on the time of day. Second, the advisory daily-changelog-rollup check also asks git which commit it checked, so whether its report names that commit or `UNKNOWN` also depends on the git found on `PATH`, its configuration and environment, and checkout filters, and on a second clock input, the elapsed time of each git call: a call that runs past its 30-second limit gives `UNKNOWN` (delta gate D8). Elapsed time is also an input of gates that put a time limit on their subprocesses, among them gates 6, 36 and 109 (a list of examples, not a complete one): the standards-currency audit (gate 6) gives each git call 60 seconds (`GIT_TIMEOUT`), and a call that runs past it ends the run with exit 2; the linter regression test suite (gate 36) runs tests that give their subprocesses time limits (`timeout=`), so a subprocess that runs past its limit can fail its test and with it the gate; and the isolated-launch import audit (gate 109) gives each tool's probe child 60 seconds (`PROBE_TIMEOUT`), and a probe that runs past it ends the run with exit 2. Third, gates that ask git also depend on what the clone holds and on the git found on `PATH`, its configuration and environment: gates 3 and 108 list tracked files from the index; gates 6, 13, 31, 40 and 45 read commit history (gate 6, in GitHub Actions, also reads the event payload); gate 59 reads `origin/main` and its merge base with `HEAD`; and the delta gates compare a change with its base revision by design. Fourth, gates 45, 59 and 78 read an optional private working-records store, when one is configured, before any in-repository `.working/` fallback, and gates 78, 81, 90 and 107 read the optional private backlog records the same way; in a clone with no such store (public CI and adopter clones) each takes its documented degrade path (next paragraph). Gates 36 and 109 also launch interpreter subprocesses, so their results depend on that interpreter. Other date-sensitive gates can have inputs beyond the current date and the repository's files too: a gate that also asks git, or reads a file outside the repository, depends on that input. Per-document date staleness (gate 31), for example, reads each file's last commit date with `git log`, run with the inherited environment and with replacement objects enabled, so its result also depends on the history the clone holds, the git found on `PATH`, and its configuration and environment. Each gate is otherwise deterministic from the inputs it reads.
2. **Stdlib-only Python (one sanctioned exception)**. Every linter is implemented in Python 3.14 standard-library code, with a single sanctioned third-party dependency: `idna` (allow-listed in gate 71, pinned in `requirements.txt`, installed in CI), used for exact UTS-46 domain-label validity in the PII gate (gate 22) and imported soft-optional with a stdlib fallback, so a bare interpreter still runs every gate. This keeps the audit programme reproducible across local, CI, and pre-commit surfaces with a Python interpreter plus the single pinned dependency.
3. **One gate, one concern**. Each gate enforces a single, narrowly defined rule. Failure messages name the rule, the file, the line, and the offending content. When a rule's domain grows beyond one file, the gate is split rather than overloaded.
4. **Conservative scope over false positives**. A gate that would produce legitimate false positives at scale is scoped narrowly to what it can track without false positives, or not shipped at all. (A gate must not keep a dormant pattern as forward scaffolding, such as an acknowledgement pattern that tracks nothing, because a permanently zero-tracking pattern adds no protection while implying coverage the gate does not provide. [`.claude/skills/corpus-management/tools/lint-cross-doc-numbers.py`](../tools/lint-cross-doc-numbers.py) kept its P1/P2/P3-acknowledgement patterns as deliberately dormant forward scaffolding in the earlier repository; they were retired there for that reason, and the gate stays active on its GDPR-breach-notification term.) Honest scope management is preferred over either silent false positives or blanket exemption lists. A permitted exception is *meta-documents* whose purpose is to describe a linter's rule set (the linter script itself, the CHANGELOG, this specification, and the Citation Verification Specification): these documents inevitably contain the patterns the linter searches for and are exempted by name in the linter's exemption list, with an inline comment naming the reason.
5. **Surface parity**. The local audit runner and the pre-commit hook must run every section 6 gate, and the GitHub Actions pull-request workflow must run exactly the CI subset that section 4 declares. Drift between the three surfaces is itself a recoverable defect rather than a feature.

Retired gate numbers are permanent recorded gaps, on the same convention as retired delta gates: the number's row keeps a one-line retired marker (a tombstone) in place of a live gate, the number is never reused and never renumbered, and a historical "gate N" reference elsewhere stays valid as a reference to the retired gate.

Most gates are pure read-only linters that exit non-zero when they find a violation; gate 72 is advisory and always exits zero, while the other exceptions to the pure-linter pattern are gates 33, 34, 85, 91, 93, and 102 (generator-output drift checks), gate 35 (audit-programme self-check), gate 36 (linter regression test suite), gate 37 (Claude-rules local-copy sync drift check), and gate 40 (corpus version-bump-recency audit, which uses `git log` heuristics to compare per-file body-commit and Version-line-commit timestamps), described below. Gates 33 and 34 re-run the generator in `--check` mode and exit non-zero if the regenerated output differs from the committed artefact. Gate 35 is the audit programme's self-check: it parses this §6 inventory and confirms that the local audit runner and the pre-commit config declare every gate with the same names and scripts in the same order, and that the workflow declares exactly the gates the §4 `ci-pr-subset` block names, with the same names and scripts in the same order (a workflow gate step outside the subset, a subset gate the workflow lacks, and a subset number that is not a live §6 gate or is out of §6 order are findings; a missing, empty or malformed block is a parse error, exit 2), and additionally that the three execution surfaces (the workflow, the local audit runner, and the pre-commit hooks) invoke each gate they hold with the same arguments (the runner and the pre-commit hooks every gate, the workflow its subset gates) and that those arguments equal the gate's entry in `GATE_ARGV`, the canonical argument table in [`.claude/skills/corpus-management/tools/lint-audit-gate-parity.py`](../tools/lint-audit-gate-parity.py) that pins every live §6 gate's flags by gate number, so a mode flag such as `--strict`, `--enforce`, or `--check` present on one surface but absent on another, or dropped or changed on every surface at once, is caught rather than letting the surfaces check different things; a live gate with no `GATE_ARGV` entry and an entry for a number that is not a live gate are findings too (the §6 Script column carries no argument, so it alone is not argument-compared; every pre-commit gate hook must run `pass_filenames: false`, so their authored flags are directly comparable). It additionally guards its own three exclusion allow-lists (cross-checking each excluded workflow setup step, workflow delta-gate step, or pre-commit hook against a positive signal that it is genuinely not a corpus gate, for example that a non-gate pre-commit hook carries no `--check`) and the cross-surface parity of the per-PR D-numbered delta gates (each numbered delta gate in the PR-time runner maps to a workflow delta-gate step of the same script, with the numbers contiguous apart from retired numbers such as D6), so a real gate mistakenly added to an exclusion set, or a delta gate mis-wired between the workflow and the PR-time runner, fails rather than being silently masked. Gate 36 is the linter regression test suite: for each in-scope linter it constructs a minimal synthetic fixture appropriate to that linter's target surface (Markdown for the corpus linters, Python source for the code linters such as gate 94) that should trigger exactly one rule, invokes the linter against the fixture, and asserts the linter exits non-zero. The test suite catches a defect class no other gate can catch (a regression in a linter's own detection logic). Gate 37 is a drift check on the project-local rule copies: it validates the pinned AIQT snapshot exactly (the pin identity, every vendored file's manifest digest, the rendered `.claude/rules/aiqt/` and `.claude/rules/security/` copies, which must be byte-identical to their vendored sources except for the declared paths-scope insertion, and the generated AIQT index block in `.claude/CLAUDE.md`), with the vendored copy digest-pinned by [`.claude/skills/corpus-management/tools/aiqt_rules.py`](../tools/aiqt_rules.py); it accepts a file under `.claude/rules/corpus-management/` only as compiler-owned through the pack's validated ownership register; it excludes the local-only `external/` overlay from the completeness check; and it fails any other markdown file under `.claude/rules/` as unowned. The `.claude/` tree is exempt from the corpus linters, so this is the only gate that catches a local copy (the file a Claude Code session loads as context) drifting from its source. It is logically akin to the generator-output drift checks (for example gates 33 and 34) but is placed last (paired with gates 38 and 39 below) so that adding it did not renumber the meta-gates above; it also verifies that every local rule file is covered by a verified owner (the pin, the compiler register, or the local-only overlay), so a new unowned rule file fails rather than going silently unchecked. The only sanctioned local difference in the rendered rule copies is the declared paths-scope insertion; the tool otherwise compares exact bytes and strips nothing before judging drift. The completeness check also recognizes COMPILER-OWNED local rule files: a file under `.claude/rules/corpus-management/` covered by a valid entry in the pack's ownership register ([`.claude/skills/corpus-management/src/core/ownership.toml`](../src/core/ownership.toml)) is accepted as compiler-owned rather than unmapped (its byte-integrity is gate 99's stricter job), while an uncovered file there still fails loud, so recognition is keyed to the validated register, never to a directory skip; an ownership entry that contests a mirrored path, sits under `.claude/rules/` outside the reserved `corpus-management/` subdirectory, or claims a block-kind target inside `.claude/rules/` is itself a finding, and an unparseable register is an internal error, so the rule mirrors and the compiler outputs can never contest a path. Gate 48 is a CSA CCM/AICM citation-accuracy audit: it loads the authoritative control reference in [`.claude/skills/corpus-management/tools/ccm_aicm_reference.py`](../tools/ccm_aicm_reference.py) (a fair-use citation index of domain codes, control-ID ranges, and canonical control titles derived from the CSA-published CCM v4.1.0 and AICM v1.1.0 catalogues, carrying none of those catalogues' normative content, so it is an index rather than a redistribution of the matrices) and checks seven things across the corpus. First, **code validity**: every `<DOMAIN>-<NN>` token whose domain is in the CCM/AICM family must name a real domain and an in-range control number (catching superseded or fabricated domains such as `IVS` (renamed to `I&S` in v4.1.0), `GRM` (the v3.0.1 governance code), `GOV` and `NET` (which do not exist), and out-of-range control numbers, such as an `IPY` control above the domain's fourth). Second, **title match** (control-listing tables only): a row (`| <CODE> | <title> |`) whose cited title shares no content word with the catalogue title is flagged as mis-attributed; the lookup is section-aware (a row under a `## CSA CCM ...` heading is checked against the CCM v4.1.0 title, one under a `## AICM ...` heading against the AICM v1.1.0 title, and one under neither against the AICM-wins union), and the check is deliberately conservative, tolerating the corpus's localized and abbreviated titles while catching fabricated ones. Third, **cross-catalogue title** (rows under a CCM/AICM section): a small set of controls share a code across both matrices but carry titles differing by a distinctive content word (I&S-07 is "Migration to Cloud Environments" in CCM v4.1.0 but "Migration to Hosted Environments" in AICM v1.1.0), which the conservative content-word check above cannot catch because the two titles share most words; this check fails a row under a CCM section that carries the AICM variant's distinctive word (and none of the CCM variant's), and vice versa. Fourth, **bare domain code** (CCM/CSA-context lines): a superseded or fabricated domain code cited as a bare token with no `-NN` suffix (a framework family list, a domain-keyed crosswalk row, a glossary-style entry) carries nothing for the code-validity check to see, so this check flags such a bare known-bad code when the line either names the matrices (CCM / CSA / Cloud Controls Matrix / AICM) or sits under a CCM/AICM section heading and is not a historical rename-note; it is precision-first (a bad code in an unlabelled multi-framework row under a generic heading is left for the apply-time grep and the periodic sweep). Fifth, **framework-as-column family** (framework-alignment tables with a CSA CCM / AICM column): the code-validity check policies only tokens whose prefix it recognizes as a CCM/AICM family (valid or known-bad), so an invented family prefix that no matrix defines (`END`, where endpoints are `UEM`; `ISM`; `GVN`, where governance is `GRC`) is silently skipped even when cited in a column explicitly headed `CSA CCM v4.1` or `AICM`; this check, scoped to that named column only, flags any control-code-shaped token there whose domain prefix is outside the CCM/AICM family as an unknown family (closing the blind spot the `ISM`, `END`, and `GVN` invented families exposed; a NIST or ISO code in a non-CCM column is untouched, and known-bad domains stay with the code-validity check, so there is no double-flag). Sixth, **framework-label-row title** (framework-alignment tables whose rows name the framework in a cell rather than in a column header): where a row carries its framework label in one cell and the code plus title in the NEXT cell (`| CSA CCM v4.1 | GRC-01 <title> |`), the code and title never reach the title-match check above, which expects the code in the row's first cell; this check flags a cited title that shares no content word with the catalogue control title (a class that occurred in the earlier repository: GRC-01 "Governance Program" was cited as "Risk Management Framework"), with an exemption for the legitimate cite-the-domain convention: a title that renders the code's DOMAIN name is exempt when more than half its content words appear in that domain name (the source-verified `DOMAIN_NAMES` map), measured on the base title before a trailing ": qualifier": IAM-15 "Identity and Access Management: PAM" is exempt on its base "Identity and Access Management" (all three words in the IAM domain "Identity & Access Management") while GRC-01 "Risk Management Framework" (one of three base words in the GRC domain "Governance, Risk and Compliance") still flags. The check is precision-first: a cell carrying two or more codes is skipped, and the more-than-half heuristic is deliberately lenient (a documented false-negative residual on a wrong title whose words are mostly domain words; a per-domain reviewed-alias table is the tighter alternative). Seventh, **bare-domain inline title** (code-first colon or parenthetical forms in explicit CCM/AICM context, or a CSA-labelled column's leading domain-plus-title value): a citation that gives a valid bare domain code with no `-NN` control number followed by an inline title, which the numbered title checks cannot see (there is no `<DOMAIN>-<NN>` token, for example `SEF: Software Engineering and Development`), is flagged when that title matches neither the domain's own name nor a uniquely best-resolving control title in the domain (a title fabricated on a bare domain code), judged by the same greater-than-half content-word threshold as the sixth check. By content, it holds 3 separate tokens in any order and with any separators, including spaces, colons and slashes: a date-like token (3 runs of digits joined by `-`, `/` or a Unicode dash from U+2010 to U+2015, read Unicode-wide, with a `T` time suffix allowed; a dot-joined year-first date with a month of 1 to 12 and a day of 1 to 31, such as `2026.11.10`; a dot-joined day-first date with a day of 1 to 31, a month of 1 to 12 and a 4-digit year, such as `10.11.2026`, which a `YYYY.MM.patch` version cannot match; a day and a month name with a year, joined by spaces, such as `10 November 2026` or `November 10, 2026`, or by those dashes, such as `10-Nov-2026` or `2026-Nov-10`; or the 8-digit form `20261110`), an X.Y.Z version (with or without a `Version` or `Library Version` label, a leading `v` or a suffix such as `-rc1`) and a numbered PR identity (a labelled PR identity as listed above, or a bare `#N`); a dot-joined token read as both the date and the version counts once. By its canonical opening, where a date-like token is 3 runs of digits joined by `-` or `/`, it starts at column 0 with `## `, `**` or `- **`, and its heading text (after `## `) or its first bold span (after `**` or `- **`) starts, after optional spaces, with `Week of` or with a date-like token that ends that text, that is followed, after optional spaces, by `,` and then a `Version` or `Library Version` label, an X.Y.Z version or a numbered PR identity that ends that text (an optional `:` or `.` aside) or is followed by `,` or `|`, or that is followed by `|` and then an X.Y.Z version or `MILESTONE:`, the cell joints of the 2 comparison shapes and the milestone form, or that text holds a `|` cell separator together with an X.Y.Z version or a numbered PR identity (`PR #N`, `PR N`, `PRs #N`, `pull N` or `#N`) that ends its cell (an optional `:` or `.` aside), the cell form of the compact shape, such as `**PR #5 | 2026.12.5**`. Every other line is not a candidate: a line without the full date, version and PR triple and without a canonical opening is body text, so `**Supersedes PR #1:** reverted on 2026-11-10.`, `**Follow-up to PR #1:**`, `**Ruling 2026-11-09:**`, `**Before | after:**`, `- **2026-11-10:** the maintainer ruled.`, `- **2026-11-10, 17:07Z:** the maintainer ruled option B.`, `**2026-11-10 | review:** done.`, `**2026-11-10 follow-up:** none.`, `**2026-11-10, PR #1 follow-up:** none.`, `**2026-11-10 | PR #1 review:** done.`, `## Ruling of 2026-11-10`, `## Follow-up for PR #1` and `**Gate 59 | 2026-11-10 review:** done.` pass, while a body line that holds a date, a version and a PR identity is a candidate by content and fails. A candidate by content, by a leading triple or as a milestone behind an opening that is not a column-0 full match of a comparison shape always fails, and no exempt shape excuses it, as an old-repository record when its first date (as defined below) is before `EPOCH_START` and otherwise with a message naming the expected shapes (or, when it is also a candidate by its opening, by the more specific rules below). An entry candidate passes only when it fully matches one of the 2 comparison shapes, `**YYYY-MM-DD | X.Y.Z | PR #N**` (optionally followed by ` - <summary>`) or `## YYYY-MM-DD, Library Version X.Y.Z, PR #N` (the bare `Version` label of the mirror's older entries reads as the same shape), with a valid ASCII ISO date, a parseable X.Y.Z version and exactly 1 PR number of 1 or more, with no leading zero in the PR number or in a version part apart from a 2-digit month (`2027.01.5`, the CalVer `YYYY.MM.patch` form), or one of the named exempt shapes: a `## Week of YYYY-MM-DD` heading, an old weekly roll-up bold line `**Week of YYYY-MM-DD (PRs #A-#B)**`, and the bold milestone form `**YYYY-MM-DD | MILESTONE:**`, whether or not its text names a PR. Every other entry candidate fails, with a message naming the expected shapes. A candidate is an old-repository record to archive only when its first date (the first year-first date joined by `-` or `/`, in any cell, with 1-digit or 2-digit months and days; when the line has none, the first date in any other form the content rule reads apart from a dot-joined year-first date, so `### 21-Jun-2026 | 2026.06.9 | PR: 3127` names `21-Jun-2026`; and when it has none of those, the first dot-joined date) is a calendar date before `EPOCH_START`, so a new entry that cites an older date later on its line is not one; a milestone dated before `EPOCH_START` is one too. The 2 weekly shapes are exempt whatever their date when they match in full with a valid date; a weekly heading or a bold `Week of` line whose date is not a valid calendar date fails as unparseable, and a bold `Week of` line that does not match the roll-up shape fails as an old-repository record when its first date is before `EPOCH_START` and otherwise as unreadable. A date that is not a valid ASCII `YYYY-MM-DD` calendar date fails as unparseable when it is the date of a line that matches a comparison shape, a weekly shape or the milestone form in full, or the date-like token right after a candidate's marker; anywhere else, as in `- 2026/11/09 | 2026.11.66 | PR #1`, the line fails with the message naming the expected shapes. A legacy line naming more than 1 PR fails because one header per PR is required, and a header naming `PR #0`, below `CUTOFF_PR`, matches no comparison shape and fails with the message naming the expected shapes. `VERSION_FLOOR` is 2026.11.66, the first version shipped by a new-repository PR (main starts at 2026.11.65): a comparison-shape header with a valid date on or after `EPOCH_START` but a version below it fails as an old-repository record whatever its date, because a date alone cannot tell an old record dated on the epoch day from a new one. As residuals, the root grammar closes its line shapes, but 3 of its rules depend on token detection: an intro line passes when the date-like, X.Y.Z version, CalVer version and PR identity detectors find nothing in it, and a weekly bullet or a canonical line's summary tail in the root passes when the CalVer detector finds nothing in it, each read as written; because every per-PR record carries a CalVer library version and the strict character rule allows only the characters it names, leaving no character or reference that renders invisibly or as another character and no link, tag, escape, code span, emphasis, inline math or brace group that could split one or join a digit to one, a record in such a line passes unread only when its version is written in allowlisted characters that the CalVer detector misses as written, such as a version split by a space, which does not render whole, or a renderer syntax made only of allowlisted characters, such as a GitHub emoji shortcode (`:one:`), which the rule does not model; the rule also restricts what an author may write in the root: every character outside the allowlist (a link's brackets, an underscore, `grc_library` among them, an angle bracket, a backslash, a tilde, a backtick, a dollar sign, a brace, a caret, a tab and every character outside printable ASCII), a `*` other than a canonical header's bold delimiters and a character reference all fail there, so such text must be written another way (a bare URL, plain words) or kept out of the root, and a file reference there is written as plain text, without backticks, so gate 11, which requires a backticked file reference in the root to be a Markdown link, finds none there; the same restriction holds every mirror canonical line, whose summary is written in the same plain form, and a mirror canonical line that does not meet it fails and is left out of the comparison; the mirror rules are open-ended: a mirror entry that has no canonical opening and lacks one of the 3 tokens (a date without a year or only in words, a version that is not X.Y.Z, or a PR named only in words or as a bare number away from the start of the line), that sits in a table row or an inline code span, or that is in any other shape none of the candidate rules reads is not detected, so a mirror-only entry in such a shape passes unread, and a root entry whose mirror counterpart is written in such a shape fails as missing from the mirror. The content rule can also fail a body line that holds a date, a version and a PR identity for another reason, because a section number such as `6.1.2` reads as a version and a version such as `2026.12.5` also reads as a dot-joined date. When no store supplies the mirror, the root's own checks still run (its readability, entry classification, and its duplicate and ordering checks), and only the checks that need the mirror are skipped. A run that compares no PR prints a DEGRADED line that says so and gives the deferred count, rather than attesting a match. In the earlier repository, three pre-split-era root headers with no detailed-mirror counterpart were an accepted exemption below that repository's floor; in this repository they are records dated before `EPOCH_START` and are archived, not exempted. Neither basis, or an unreadable merge-base changelog, origin/main changelog or origin/main log, disables all deferral and prints a note. D1 can accept a `Changelog: <one-line-reason>` trailer; it does not guarantee an own entry before merge. Every deferred mirror header is printed with its location, named PRs and reason. One pass over this whole specification pairs them in context, as CommonMark does: a fence opens on a line of up to three spaces and then three or more backticks or tildes (a backtick fence's info string holds no backtick) and closes only on a line of the same character, at least as long, with nothing else on it, so a fence line with an info string inside a fence is fence text; outside fences and comments, inline code spans (a run of backticks to the next run of the same length on the line) are blanked before a comment opener is looked for, so a comment opener quoted in a code span, as in the gate 70 and 104 paragraphs, or shown in a fenced block opens nothing; an open comment ends at its first comment closer in the raw text, inside backticks or not; and a fence line inside a comment is comment text. A fence or comment that never closes before the end of the file is a finding at its opening line, and the category lists are then not compared. A forgotten opener that pairs with a later block's closer is not itself a finding, and what it hides decides the result: placed before section 5 it hides the section 5 heading, which is reported as a missing section 5; placed among the category lines it hides the lists after it, whose numbers are reported missing unless they are listed elsewhere; placed after the lists or in this section, it hides only section 5 prose after the lists and text of this section (a stray backtick fence just before the fenced block that follows the gate 73 paragraph pairs with that block's closer), which this check does not read (the inventory rows are read without the markup pass), so no finding is reported. A section 5 line that starts like a numbered or bulleted list item with `*` or `_` emphasis (`8) **`, `8. *`, `8. __`, `- **`, or an indented item) without that exact list shape, all on one line, is a finding, and so is a missing section 5, so a reformatted or wrapped list fails loud instead of being skipped; the lists are then not compared either. Which category a gate belongs in stays a review judgment.

Added forms in other cases and single-word candidates are intentionally outside this precision-first check. Delta gates D1, D2, D3, D4, D7, D11 and D15 resolve the pull request range with one shared resolver ([`lint_common.resolve_pr_range`](../tools/lint_common.py)), and each compares the head with a single merge base. The resolver therefore refuses such a range and names every merge base: D1, D2, D3, D4, D7 and D11 exit 2, and D15 prints a note and exits zero. Merging the base into the branch, or rebasing the branch onto the base, leaves one merge base. D12 reads its merge bases itself, as its paragraph below describes.

Delta gate D1 mechanically enforces §7 step 4 below ("the CHANGELOG entry for the phase is written"): it compares the PR head to its merge-base with the target branch and fails when [`.working/CHANGELOG.md`](../../../../.working/CHANGELOG.md) is not in the diff. Delta gate D4 enforces the Version-Date co-bump half of the version-bump discipline: when a PR bumps a versioned document's `**Version:**` field, the same change must set that document's `**Date:**` field to the date its Version-bumping commit was made (UTC). Delta gate D7 enforces the compact-form length ceiling on [`.working/CHANGELOG.md`](../../../../.working/CHANGELOG.md), but only on entries a PR adds. `.working/CHANGELOG.md` carries one SHORT one-line summary per change (the `**date | version | PR** - summary` compact form); the full maintainer-grade detail lives in the detailed mirror (in the optional private operational store) and in git history. Delta gate D8 is the advisory daily-changelog-rollup reminder ([`.claude/skills/corpus-management/tools/check-daily-changelog-rollup.py`](../tools/check-daily-changelog-rollup.py)): at PR time it scans [`.working/CHANGELOG.md`](../../../../.working/CHANGELOG.md) for any UTC date strictly before today that still carries more than one per-PR entry (never collapsed into that day's single daily roll-up), and WARNS `DAILY SUMMARY DUE for <date>` naming each such date. Each such line follows a machine-readable `D8 DUE id=D8-<date>@<rev12|UNKNOWN> date=<date> count=<n> due_since=<date+1>T00:00:00Z` line, and the report is framed by `D8 BEGIN rev=<40hex|UNKNOWN> today=<date> run=<64hex>` and `D8 END rev=<40hex|UNKNOWN> today=<date> run=<64hex> due=<n> rc=0` lines. `run` is the SHA-256 (hex) of the UTF-8 text `rev=<rev> today=<date>`, a LF, then every line between BEGIN and END, each followed by a LF. Reader rule: a report is complete only when its BEGIN and END lines carry the same `run` and name the same `rev` and `today`, `run` recomputed over that `rev`, that `today` and every line between them equals it, and the END line ends `due=<n> rc=0` with `<n>` the number of `D8 DUE` lines between them. A BEGIN or END line counts only when it matches its whole grammar line above, with no other text anywhere on it, so an END line with a token added between `run=` and `due=`, or after `rc=0`, is not an END line. Anything else is not a complete report: a BEGIN with no such END, lines cut from or added to the lines between (a run's BEGIN and END around another run's lines), or an END line cut short or altered after `run` (`due=` and `rc=` are outside the digest, so the count is checked on its own). `rev` is the HEAD commit only when the checked CHANGELOG is byte-identical to that commit's blob, read with git replacement objects disabled; otherwise it is `UNKNOWN`, and the DUE id ends `@UNKNOWN`. A report carries no time of day. It has two clock inputs: the UTC date, and the elapsed time of each git call, which has a 30-second limit (`GIT_TIMEOUT`), so a call that runs past it makes `rev` `UNKNOWN` where a quicker one would give the SHA. Its other inputs are the CHANGELOG bytes and `rev`, and `rev` depends on more than the repository, so the current date is not D8's only input from outside the repository. Two qualifications apply: the git environment decides whether a revision is available at all (a SHA or `UNKNOWN`), and the human line after `D8 NOT-FOUND` or `D8 REFUSED` also depends on the path as given, the interpreter, the operating system and stdout's encoding. Whether `rev` is a SHA or `UNKNOWN` also depends on the git found on `PATH`, its configuration and environment (`GIT_DIR` selects the repository; a broken `GIT_CONFIG_GLOBAL` or the `safe.directory` ownership check makes git fail; a SHA-256 repository gives no 40-hex SHA) and checkout filters (CRLF conversion makes the working-tree bytes differ from the blob), so the same CHANGELOG at the same commit can give the SHA in one environment and `UNKNOWN` in another. This fails safe: UNKNOWN never names a commit, and a SHA is printed only for its blob's exact bytes. The blob is read at the commit the first git call returned (`<rev>:./<name>`), never at `HEAD` again, so a HEAD that moves between the two calls cannot bind one commit to another commit's bytes. In CI, where D8 runs only for a pull request, `rev` is GitHub's temporary merge commit of the pull request's head into its base branch (the workflow's default checkout), not the head commit itself. When there is nothing to report, D8 prints no BEGIN or END but one machine-readable line and a human line naming the path: `D8 NOT-FOUND today=<date> rc=0` when the path resolves to nothing (no entry, a dangling symlink, or a component that is not a directory), or `D8 REFUSED reason=<unreadable|not-utf8|bad-date> today=<date> rc=0` when the path cannot be read, the CHANGELOG is not UTF-8, or it has a per-PR entry whose date is impossible or not written in ASCII digits. One malformed per-PR date refuses the whole report (`D8 REFUSED reason=bad-date`), so no other due date is reported until that line is fixed. This is deliberate (stricter is safer): a partial report would read as complete. Only an open failing with ENOENT, or with ENOTDIR because a component of the path is not a directory, is `D8 NOT-FOUND`; any other error opening or reading the path, or a path that is not a regular file, is `D8 REFUSED reason=unreadable`. The machine-readable lines carry neither the path nor any error text; the human line after `D8 NOT-FOUND` or `D8 REFUSED` also carries the path as given and, after `D8 REFUSED`, error text specific to the interpreter and operating system (the system's error message, or the UTF-8 decoder's or the date parser's message). The path is the `--changelog` argument exactly as given, not pathlib's normalized form. A character in the human line that stdout's encoding cannot represent is written as a backslash escape, so neither the path nor the error text can stop D8 exiting 0; every report line is ASCII by construction. Whatever stdout's encoding and error handler, every character in the human line outside printable ASCII (0x20 to 0x7E) is written as a backslash escape (`\x0a`, `\x85`, `\u2026`, `\udc85`) before the line is written, so the human line is plain ASCII and no encoding sees any other character in it. Escaping only the controls, U+2028, U+2029 and the surrogates was not enough, because a non-ASCII character left unescaped can encode to a byte that another encoding reads as a line break: cp1252 writes U+2026 as the byte 0x85, which ISO-8859-1 reads as a line break (NEL), and that set left U+2026 unescaped. Surrogates are escaped because the `surrogateescape` error handler writes a surrogate (a path byte that is not UTF-8 decodes to one) back as that byte. Under an encoding that writes ASCII as ASCII (UTF-8, ISO-8859-1 and cp1252 among them), read by a reader that reads ASCII as ASCII, the human line is therefore exactly one line, always begins `check-daily-changelog-rollup: `, and no path or error text can make D8 print a line of the grammar above. An encoding that does not write ASCII as ASCII (cp037, an EBCDIC code page, writes `e` as the byte 0x85; UTF-16 writes two bytes per character) changes every line D8 prints, the machine-readable lines too. A backslash is printed as is: the human line is for people, not for parsing. argparse's usage error on stderr is escaped the same way, its message (which quotes an unknown argument) and the program name, so an argument cannot make D8 print a line of the grammar above either. D8 also opens the `--changelog` argument exactly as given: an empty argument fails with ENOENT, and a regular file named with a trailing `/` or `/.` fails with ENOTDIR, so each is `D8 NOT-FOUND`; only the revision lookup uses the normalized form's directory and name. Git failing, absent, timing out or printing output that does not decode refuses only the revision (`rev=UNKNOWN`), and the report still runs. Each git call reads no standard input and has a timeout, and a timeout is a git failure like any other. It is ADVISORY (exit 0 in each of these cases, never blocks) because a hard failure would wrongly block a genuine hot-fix on a day whose roll-up is merely pending; its purpose is to surface the reminder in every pull request's pre-push and CI output so the daily summarization is actioned rather than silently skipped. The exceptions to exit 0, a complete list, all lie outside D8's checking of the CHANGELOG: an unknown option or a missing option value is argparse's usage error (exit 2); a run with no usable stdout, as when the process starts with file descriptor 1 closed (Python then sets `sys.stdout` to None, and `print` writes nothing) or stdout's descriptor or stream is closed, is refused before anything is checked, and its exit is non-zero in every case, so a report that could not be delivered never reads as a pass. When stderr is writable, D8 writes one line giving the reason to stderr and exits 3; with no stderr at all (file descriptor 2 also closed at startup, so `sys.stderr` is None) it writes nothing and exits 3. This check runs first, before the options are parsed, so with no usable stdout an unknown option, `--help` and `--self-test` are refused the same way. When stderr exists but cannot be written (the device is full, as on /dev/full), the exit is still non-zero: D8 catches the failed write and returns 3. Which code the process ends with depends on stderr's buffering: unbuffered (`python3 -u`), nothing is left to write and the exit is 3; with stderr's default buffering, the unwritten line stays in stderr's buffer, the interpreter's final flush of it fails again, and the exit is the interpreter's flush-failure status instead. Only a non-zero exit is part of this contract for this case (observed on CPython 3.14.4: 3 unbuffered, 120 buffered); a write to stdout that fails, because the reader has closed it (a broken pipe) or the device is full (ENOSPC, as on /dev/full), is the interpreter's error, and D8 then exits non-zero, never 0, with no complete report delivered. The exact code depends on when the write fails and is not part of this contract, nor is the wording of the interpreter's message on stderr. Observed on CPython 3.14.4: 120 when only the interpreter's final flush of stdout fails (block-buffered, a pipe or a file, the default, with a report smaller than the buffer); 1 unbuffered (`python3 -u`), where the first line D8 prints fails; and 120 when, block-buffered, a write fails mid-run (a report larger than the buffer, 128 KiB on Python 3.14), because the final flush then fails again. Exit 120 on a failed final flush has been CPython behaviour since 3.6 (the `sys.exit` documentation). CI runs Python 3.14 (the workflows set `python-version: "3.14"`), not necessarily the observed 3.14.4 release; another release's buffer size can differ, which changes only which of these cases a given report reaches; `--self-test` exits 1 when one of its cases fails; a usage error or `--self-test` (which reports its cases on stderr) may end with the interpreter's own status instead when stderr is absent (file descriptor 2 closed at startup) or cannot be written (the device is full, as on /dev/full). Observed on CPython 3.14.4: `--no-such-option` exits 120 with stderr on /dev/full under stderr's default buffering (2 unbuffered, and 2 with no stderr), and `--self-test` with every case passing exits 120 with stderr on /dev/full (1 unbuffered) and 1 with no stderr. A checked run and `--help` write nothing to stderr, and were observed to exit 0 in each of these cases; a signal that terminates the interpreter ends D8 with that signal's status, as does a failure of the interpreter itself (it cannot start, or runs out of memory). The daily roll-up collapses a past day's per-PR entries in `.working/CHANGELOG.md` into one `**date | version | PRs #A-#B (N PRs)**` summary that stays there while its week is current (a completed week's daily summaries are then rolled up into one weekly PR-range summary), and the matching detailed-mirror entries are swept to the private archive; the history in `.working/CHANGELOG.md` is never removed, only summarized in place. A date already in roll-up form, a date with a single entry, and today's per-PR entries are all correctly ignored.

The central compliance matrix is out of scope (its cross-document consistency is the `/matrix-fit` cadence's concern). Measured false-positive rate zero over the prior 80 commits; it is deletion-triggered and same-document only, a defence-in-depth layer under the multi-family QA that catches this class only sometimes.

Delta gate D15 is the advisory alignment-citation register check ([`.claude/skills/corpus-management/tools/check-alignment-register-on-pr.py`](../tools/check-alignment-register-on-pr.py)): it WARNS when a pull request adds a citation of a standard or regulation that has no row in the canonical-citations register ([`register-canonical-citations.md`](../../../../governance/register-canonical-citations.md)), the register's own "add an entry here before the citing PR merges" maintenance rule, which nothing enforced (on 2026-10-04 a pull request in the earlier repository cited the Critical Entities Resilience Directive and the Commission Recommendation defining micro, small and medium-sized enterprises by instrument number in prose, with no row for either). The exclusion policy is data, [`.claude/skills/corpus-management/tools/alignment-register-exclusions.json`](../tools/alignment-register-exclusions.json), which encodes the "Tracked only" scope: the register covers standards and regulations whose currency is tracked, so an unregistered RFC, vendor guidance or book is not reported; each policy pattern or entry names its class and its reason, and the file is validated on load. Once its modules load, the check exits zero whatever it finds, following the advisory precedent of D8 (whose own exceptions to exit 0, a usage error, a run with no usable stdout, a failing stdout write, a failing self-test, a usage error or self-test with stderr absent or unwritable, a signal and a failure of the interpreter itself, the D8 paragraph lists), and it is deliberately absent from [`.claude/skills/corpus-management/tools/run_all_audits.sh`](../tools/run_all_audits.sh): that runner hides a passing gate's warnings, and a corpus gate must carry a near-zero false-positive rate, which an alias-dependent name match cannot promise. D15 reads the register at `--register-ref` when it is given and at the head otherwise. A register that is absent there (an adopter may drop it) or cannot be read ends the run, and so does a changed document in scope whose diff or head content cannot be read. Each of these, a missing merge base or more than one, and a failed `git diff` of the changed file names ends the run before the sibling probe described below, with only its own printed note and no note that the probe was skipped. A head without the register does not end a run with a `--register-ref` that has one: the main check reads that ref's register, and the probe compares the head's absent register as one with no rows, so when the pull request deletes the register every Standard ID of the merge base's register counts as removed. An unreadable policy file is a printed note and a no-op for the main check; the sibling probe still lists siblings then only when the file that failed is the alias file in the checkout (absent, unreadable or malformed), which the probe does not read; it also needs the exclusion policy in the checkout, a register that parses, and a head alias file that is absent or loads, and it prints a note that it was skipped when one of them fails. Replayed across the 120 first-parent commits that ended the earlier repository's history at that point, with the register as shipped, D15 produced 33 added-citation warnings in 12 commits (including the lines of that 2026-10-04 pull request), and the final 20 of those commits produced none; these advisory warnings require review and do not by themselves establish that a register row is missing. It is delta-only and recognizes only those four surfaces, so an instrument named in prose without a number, or a citation already on `main`, is outside its reach (gate 6's report mode inventories the latter for its grammar families). When the pull request changes the alias file or the register, the same run adds a report-only sibling probe with no gate number of its own: it scans the three alignment-table surfaces across the whole corpus at the pull request head and prints a `D15 SIBLING` line for each citation that is still unregistered and shares a distinctive token with an alias key that the pull request adds, removes or retargets, or with a register Standard ID that it adds or removes, so that another form of the same instrument, or a related instrument, can be found in the same revision of the pull request (in one pull request of the earlier repository, an early revision aliased `US TSA Pipeline Security Directives` while the related sibling row `US TSA Rail Cybersecurity Directives`, a separate TSA directive set, kept warning until a later revision). The probe compares only the set of Standard IDs: a row whose Standard ID is edited counts as the old ID removed and the new one added, and an edit to a row's other cells (a date or a version) changes nothing, so on 2026-10-17 in the earlier repository, a synthetic edit that moved every date in the `Last verified (UTC)` cells of all 23 register tables one day later listed nothing. That edit changed 217 dates in 216 of the 219 rows of those tables: 189 of the 192 Standard ID rows, and the 27 rows of the AI security tooling references table, which is keyed by `Project` and which gate 6 does not parse; the other 3 rows read `needs-reconfirm`. Taking each of those 189 Standard IDs as changed lists 86 citations. The probe resolves citations with the head's alias file, and treats an absent one as an empty map; the main D15 check reads the alias file in the checkout, which in CI is the commit checked out as the head (the pull request merge ref), and both read the exclusion policy in the checkout. With `--register-ref`, the family tokens and the judgement of which citations are unregistered use that ref's register. A distinctive token is a designator mixing letters and digits, a number of three or more digits that is not a year, or a word of three or more letters outside a stop list of function words, words that name a kind of instrument, a topic or a jurisdiction, and generic words that paired unrelated instruments of different publishers (`party`, `assessment`, `access`, `design`, `provisions`, `certification` and others); accents are removed first (NFKD, combining marks dropped), so the accented and unaccented spellings of `Quebec` match. In every case the token must also appear in fewer than ten register Standard IDs (in the earlier repository on 2026-10-17, `ISO`, `IEC`, `NIST`, `800` and `Canada` named families of rows and were not distinctive). The probe lists in two tiers so that a citation sharing only a distinctive word is still listed and the noise stays visibly weak. A citation that shares a changed entry's acronym (a word with a capital after its first letter, such as `TSA`, `MiCA` or `GenAI`), designator or number is a `D15 SIBLING` line. A citation that shares no acronym, designator or number with any changed entry and a distinctive word with at least one is a `D15 SIBLING (word match)` line, printed after the strong lines with the shared words named. For example, the spelled-out `Transportation Security Administration Pipeline Security Directives (SD Pipeline-2021-02G)` shares only `pipeline` with the former alias key `US TSA Pipeline Security Directives` (the key is not in the alias file; a test adds it back as a fixture); a review in the earlier repository found it lost when an entry with an acronym was matched on its acronym alone. A word match is weak evidence and is often a different instrument. A NOTE line names each changed entry with no distinctive token, and any change to the alias file's `umbrella` or `not_citable` entries, which the probe does not compare. The probe never changes the exit status. Its residual is printed beside its result. Not listed are: a form that shares no distinctive token with the changed entry (`Law 25` beside `Quebec Law 25`, or a spelled-out name beside its acronym that shares no distinctive word with it, such as one sharing only stop words or family tokens: `Cloud Security Alliance Cloud Controls Matrix v4.1` beside `CSA Cloud Controls Matrix`); every form of a changed entry with no distinctive token; a form sharing only a family token (the family tokens of the register in use are printed); a sibling outside the three alignment-table surfaces (prose, an EU/EC number or another table); and the siblings of an `umbrella` or `not_citable` change. A listed citation can also be a different instrument from the same publisher.

## 7. Phase-completion gating

A phase is complete when:

1. All file edits intended for the phase are written.
2. Auto-generated artefacts ([`.claude/skills/corpus-management/data/taxonomy.yml`](../data/taxonomy.yml), [`.claude/skills/corpus-management/data/narrative.yml`](../data/narrative.yml), [`governance/portal.md`](../../../../governance/portal.md), [`governance/maturity-scorecard.md`](../../../../governance/maturity-scorecard.md), [`governance/relationship-model.generated.json`](../../../../governance/relationship-model.generated.json), and the generated `## Number allocation` block in [`.working/TODO.md`](../../../../.working/TODO.md)) have been regenerated.
3. The full audit programme passes locally via [`.claude/skills/corpus-management/tools/run_all_audits.sh`](../tools/run_all_audits.sh).
4. The CHANGELOG entry for the phase is written.
5. The library calendar version is bumped (and the README version where appropriate).
6. The change is committed and pushed; the pull request is opened.
7. The GitHub Actions `Lint markdown corpus` check (the CI subset and the delta gates) and the `local-quality` commit status (the full gate suite on the local server) both confirm green.
8. The pull request is merged and the local branch is fast-forwarded to the merged main.

Selective subset runs are not a substitute for the full sweep. This rule was established after a merge in the earlier repository that bundled several phases introduced five gate violations that a full local sweep would have caught.

## 8. Audit programme failure handling

When an audit gate fails, the maintainer (or AI verifier) must:

1. **Read the failure message in full.** Each gate prints the offending file, line, and content.
2. **Locate the underlying cause.** Do not edit the linter to suppress the finding without first investigating whether the linter is correct.
3. **Choose between three responses:**
    1. **Fix the content.** This is the default response. The content is in violation of a documented rule; the content is corrected.
    2. **Extend the linter's exemption list.** Only when the content is correct and the rule does not apply (e.g., the [`.claude/skills/corpus-management/tools/lint-citations.py`](../tools/lint-citations.py) `COBIT 2025` exemption granted to documents that *deliberately* discuss the hallucinated framework version as a warning). The exemption must name the file by relative posix path and is recorded inline next to the existing exemption set.
    3. **Modify the rule.** Only when the rule itself is wrong (e.g., loosening [`lint-required-sections.py`](../tools/lint-required-sections.py) to accept Purpose OR Scope OR Applicability OR Introduction OR Overview). Rule modifications require an entry in the CHANGELOG and a corresponding update to the linter's module docstring.

Bypassing a hook (`--no-verify`, `--no-gpg-sign`, etc.) is not a permitted response. If a hook fails, the underlying defect is fixed before commit, not bypassed.

## 9. Adding a new gate

A new gate is added when:

1. A class of defect is identified that current gates do not catch.
2. The defect is deterministically detectable from repository state without network access or third-party dependencies.
3. The signal-to-noise ratio of the proposed rule is acceptable (false-positive rate is empirically zero or near-zero on the current corpus).

The procedure for adding a gate:

1. Write the linter as `.claude/skills/corpus-management/tools/lint-<feature>.py` (Python 3.14, stdlib only).
2. Confirm the linter exits 0 on the current corpus (zero false positives).
3. Add the gate to [`.claude/skills/corpus-management/tools/run_all_audits.sh`](../tools/run_all_audits.sh), [`.pre-commit-config.yaml`](../../../../.pre-commit-config.yaml), and the §6 inventory table above. Add it to [`.github/workflows/quality.yml`](../../../../.github/workflows/quality.yml) and to the section 4 `ci-pr-subset` block only when it joins the CI subset; otherwise it runs locally and behind the `local-quality` commit status. Add the gate's entry to `GATE_ARGV`, the canonical argument table in [`.claude/skills/corpus-management/tools/lint-audit-gate-parity.py`](../tools/lint-audit-gate-parity.py), keyed by its gate number and holding the flags the runner passes it (an empty tuple for none); gate 35 fails on a live gate with no entry.
4. Add the new gate's row to the §6 inventory; §5 places the gate in its functional category. The §6 inventory table is the canonical source of truth for the gate count.
5. Record the addition in the CHANGELOG under a new phase entry.

## 10. Modifying or retiring a gate

A gate is modified when its rule is found to be incorrect. The modification must include:

1. The corrected linter code.
2. A re-run of the full audit sweep to confirm no new violations surface.
3. A CHANGELOG entry naming the gate, the rule that changed, and the rationale.
4. An update to the linter's module docstring if the rule's substance changed.
5. When the change adds, removes or changes a flag the surfaces pass the gate, the same change to the gate's `GATE_ARGV` entry in [`.claude/skills/corpus-management/tools/lint-audit-gate-parity.py`](../tools/lint-audit-gate-parity.py), since gate 35 compares every surface's arguments with that entry.

A gate is retired when its rule is found to be unhelpful, dominated by another gate, or producing structural false positives that cannot be narrowed. Retirement requires a documented rationale. A retired gate's number is a permanent recorded gap: it is never reused and never renumbered, and the §6 inventory keeps a one-line retired marker (a tombstone) in the number's row recording the date and reason, so historical "gate N" references stay valid as written. Retirement also removes the gate's `GATE_ARGV` entry from [`.claude/skills/corpus-management/tools/lint-audit-gate-parity.py`](../tools/lint-audit-gate-parity.py), since gate 35 reports an entry for a number that is not a live gate.

## 11. Relationship to the Citation Verification Specification

The Audit Programme Specification and [`governance/specification-citation-verification.md`](../../../../governance/specification-citation-verification.md) form a complementary pair:

| Concern | Governed by |
| --- | --- |
| Are the library's internal references, structure, naming, metadata, and language internally consistent? | Audit Programme Specification (this document) |
| Are the library's claims about external standards accurate against publisher canonical sources? | Citation Verification Specification |

Three of the gates sit at the boundary between the two programmes:

- [`.claude/skills/corpus-management/tools/lint-citations.py`](../tools/lint-citations.py) (gate 5) detects literal-string drift on external framework versions (for example, the canonical "COBIT 2025" hallucination warning). Its substance is a claim about the world (what version of COBIT is current), which derives from the Citation Verification Specification; its mechanism is deterministic repository-state pattern matching, which is the audit programme.
- [`.claude/skills/corpus-management/tools/lint-citation-verification-freshness.py`](../tools/lint-citation-verification-freshness.py) (gate 27) and [`.claude/skills/corpus-management/tools/lint-tooling-provenance-freshness.py`](../tools/lint-tooling-provenance-freshness.py) (gate 28) enforce the freshness cadences (12-month for canonical citations, 6-month for active tooling, 12-month for archived tooling) defined in Citation Verification Specification §12.

These three gates are determined automatically from repository state (so they belong to this programme) but enforce semantics defined in the Citation Verification Specification (so their substance derives from there).

When the two specifications conflict, the Citation Verification Specification governs the *substance* of what counts as "verified" and "fresh"; this specification governs the *enforcement mechanism* by which that substance is checked at every change.

## 12. Out-of-scope acknowledgements

The audit programme does not, and cannot, detect:

- **Substantive correctness of content.** A linter cannot detect that a paragraph asserts something untrue about the world; that is the domain of human review and (for external claims) the Citation Verification Specification.
- **Architectural coherence.** Whether a new document is well-placed in the library's information architecture is a human judgement, not a machine-detectable property.
- **Semantic duplication.** Two documents that say the same thing in different words pass every gate; identifying such duplication is part of the manual review cadence.
- **Adopter usefulness.** Whether a document is actually useful to a downstream adopter is not testable from repository state alone.

These limitations are not defects in the audit programme; they are the natural boundary at which automated quality gates stop and human judgement begins. The audit programme is a necessary but not sufficient condition for library quality.
