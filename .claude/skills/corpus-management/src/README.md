# Corpus-Management pack (`.claude/skills/corpus-management/src/`)

**Status: ACTIVE.** This directory is the source of a standalone, adoptable Corpus-Management
pack: the compiler, the source of the CLAUDE.md generated-artefacts instruction block, the
file-kind rules (among them the corpus language convention and the corpus authoring conventions),
and the mandatory drift gate (grc gate 99). The gate register (`core/gates.toml`) lists each
of the 54 transferred gate engines and its wrapper entry point; each entry's origin note names
the grc gate it serves. The hook register (`core/hooks.toml`) holds no transferred hooks.
Gate 98 (vendored-core digest) runs as a corpus gate for now, and publication of the pack is
deferred; the `[rollout]` table of `core/manifest.toml` records both.

## What this is
A **thin, adoptable layer** for keeping a documentation corpus internally consistent (metadata shape,
section model, citation currency, cross-links), built on top of the **AIQT generic core** rather than
duplicating it. The generic file/text/date/git/metadata primitives come from the vendored
`aiqt_corpus` module (consumed from the upstream AIQT project; see `.claude/aiqt/`); this pack adds
only the corpus-specific policy: the fixed metadata structure, the register grammar, and the corpus
gates/hooks. AIQT provides policy-free primitives, not a corpus compiler; this pack is that
compiler's source of record.

## Source-of-record discipline
`.claude/skills/corpus-management/src/` is the **authoritative source**. Generated outputs (rules, CLAUDE.md blocks,
gate/hook wiring) are produced FROM this tree by the compiler (`tools/corpus_mgmt_compiler.py`,
wrapped by the project's `.claude/skills/corpus-management/tools/build-corpus-management.py`) and are **never edited directly**; edit
the source here and regenerate. The drift gate (grc gate 99, the wrapper's `--check` form) enforces
byte-parity with nothing stripped before comparison.

The compiler's managed-output stray scan (`_managed_drift` in `tools/corpus_mgmt_compiler.py`)
covers `.claude/rules/corpus-management/`, `.claude/references/corpus-management/` and the skill
directory `.claude/skills/corpus-management/`, where the compiler owns only its declared targets
(`SKILL.md` and `rule-index.md`). In the skill directory the scan skips the shipped entries that
`CM_SKILL_SHIPPED` names (`adopter-config.json`, `data`, `docs`, `procedures`, `registers`, `specs`,
`src`, `tests` and `tools`) and everything beneath them, unless the entry is itself a symlink. Any
other file that is not a declared target, any other symlink (a declared target included), and a
symlink in place of a shipped entry fail `--check` (exit 1) and generation (exit 2). In the earlier
repository, after the pack moved under `.claude/skills/corpus-management/src/`, and until the
2026-11-08 change that added this skip, the scan walked the whole relocated skill directory and reported every shipped
tool, test, data file and document as an unexpected file, so gate 99 could not pass.

Only `language-convention.md` and `normative-wording.md` load from
`.claude/rules/corpus-management/`. The other 52 bodies live in `.claude/references/corpus-management/`,
where Claude Code does not auto-load them. The generated rule index,
`.claude/skills/corpus-management/rule-index.md`, ships in the corpus-management skill directory
and is read when the skill loads, on the skill's instruction, not at session start. The index
lists each rule, its source-heading purpose, enforcing tool(s), and body path. Read the body
before editing files its gate scans or when a gate fails. Bodies retain their source bytes and
provenance header; gate 99 owns all generated bytes.

## Scan boundary (why this directory is exempt from corpus-content gates)
This is pack SOURCE, not corpus content, so the corpus-content validators do not select it (a
root-anchored exemption, `lint_common.DEFAULT_EXEMPT_ROOTS`, matched as a prefix of the
repository-relative path, so a nested or similarly named directory does not acquire it). The security and cross-cutting operational audits
(secrets, PII, internal-references, external-link-domains, narrative-boundary, and prose dash-style)
**still apply** to this tree; the exemption is from corpus-document-model validation only, not a blanket
skip. (The stdlib-only-imports and unused-import gates scan the pack's `tools/` tree, which ships
Python.)

## Structure (fixed) vs vocabulary (configurable)
The metadata STRUCTURE is fixed (every document carries the same field set and section model, which is
what makes the corpus machine-auditable). The VOCABULARY (allowed values, jurisdiction lists, framework
identifiers) is configurable per adopter via profiles under `defaults/`.

## Reference and operational registers
Reference defaults ship under `defaults/grc/` and are overridable by an adopter. Operational registers
(a project's private working state) are **project-only** and are never shipped by this pack.

## Optional semantic add-ons
The reference-dependent semantic audits (matrix-fit, claim-fit, reference-audit,
publication-screening) are OPTIONAL add-ons that require an adopter to supply a reference base; they
are listed in the manifest as available but disabled in the skeleton. The `[addons]` register is
adopter availability only (no pack or project tooling acts on it; only the pack activation
test asserts its contents); listing publication-screening there
does not relax the parent project's own publication screening (`/screen-publications` in its
CLAUDE.md), which stays required unconditionally.

## Language profile (gate 2)
The `language` profile (`defaults/grc/language.toml`) carries an `ise_prefixes` key beside
`ise_stems`, and the engine's `language_vocabulary()` requires it. An adopter `language` profile
override must add `ise_prefixes`; an empty array keeps the stem-only pattern. Each
prefix must be ASCII letters only, and `compile_language()` raises `ValueError` on an empty
`ise_prefixes` or `ise_stems` entry. Any run of listed prefixes, with a hyphen after up to three of
them, may precede an `ise_stems` entry inside the same word bounds, so a prefixed derivative
("reorganised", "de-emphasised") needs no stem entry of its own, while a word that only begins
with a prefix ("premise", "devise") is not reported, because no listed stem ends it.

## URL masking (gate 2)
The language engine (gate 2) masks scheme-qualified `http` / `https` URL tokens out of the three spelling checks through the public `mask_urls(line)` helper, called from `spelling_matches()`, so the CHANGELOG preflight aid that shares the matcher gains the same exemption. A URL is an external identifier whose spelling cannot be changed (the UK ICO `for-organisations` guidance path). `mask_urls` runs before the allowed-span mask, so an allowed span inside a URL cannot split it, and applies wherever the token occurs: bare, in an inline code span, as a link target, in a reference-style link definition, as an autolink, or in a generator string literal. The scheme (any case, ASCII letters only), preceded by a non-word character or by a `_` / `__` emphasis delimiter that is itself preceded by one, needs a real authority (dot-separated host labels whose top-level label is all lowercase letters, or all uppercase letters when no host label contains a lowercase letter, or a bracketed literal that the standard library's `ipaddress` module accepts as an IPv6 address, optionally a port) and continues only with a path, query or fragment starting with `/`, `?` or `#`; the token stops at whitespace, a backtick, `<`, `>`, a double quote, `|`, `*`, `{`, `}`, a square bracket, a backslash, `^`, `~~`, a `%` not followed by two hexadecimal digits, an ASCII control character, any non-ASCII character and an unbalanced parenthesis (one level of balanced parentheses in the path is kept), and, when the scheme follows a `_` / `__` delimiter, at a run of one or more `_` followed by anything other than an ASCII letter or digit, so prose after the closing delimiter is checked, while a run of `_` followed by an ASCII letter or digit continues the token, as a path underscore does (the `___` of a path such as `/a___b` continues the token); `.,;:!?` continues it only when no letter, `-`, `_`, `~`, `+`, `@`, `$`, apostrophe, `(`, `)`, `&`, `%`, `=`, `#` or `/` follows, directly or after a run of digits (the `:` of a nested `http://` or `https://` continues), a dot before letters only as a lowercase extension of one to six characters ending the segment, and an apostrophe only as a possessive `'s`; `?` continues it whenever a query key reaches `=`, the key being any run, possibly empty, of letters, digits, `.`, `_`, `~`, `+`, `-` or `%` escapes of two hexadecimal digits, so `?-key=1`, `?_key=1`, `?1key=1` and `?=value` are masked like `?key=1` whatever word they hold (an accepted over-mask), and any other `?` before a letter ends it; trailing `.,;:!?` is trimmed. Only the URL is masked: a link's visible text, a non-URL code span and prose separated from the URL by whitespace or a delimiter are checked, and prose glued to a URL is checked from where the token ends (under-masking, a false positive, is preferred to over-masking, a bypass). Residuals that stay checked as false positives: a URL wrapped across lines, a host with no dot or a numeric or mixed-case top-level label, an all-uppercase top-level label after a host label with a lowercase letter, a URL with userinfo, path text after a punctuation run the rules end at (including the part of a dotted version such as `v1.2/` from the dot on), path text after a `_` (or run of `_`) followed by anything other than an ASCII letter or digit (in an emphasized URL), text after a `_` run followed by anything other than an ASCII letter or digit in a URL after a literal `_` or `__` that is not emphasis (for example in an inline code span or a string literal), which is read with the emphasis rule, text after any non-ASCII character (not only a letter) in a URL path, query or fragment, which ends the token (a URL path such as `/réorganisations` reports `organisations`), and a URL whose host holds a non-ASCII character, which is masked only up to the end of the last ASCII label before the character that can end a host, and not at all when no such label precedes it, as when the character is in the first label. A host is masked as written, so a checked word written as a host label is not reported, including a lowercase word glued by a dot to a URL with no path or an all-uppercase word glued to an all-uppercase host, a valid top-level label the engine cannot tell from a real one without a top-level-domain registry (an accepted over-mask). No word-level exception is added, and the dash, `ensure that` and heading-case checks are unchanged. The language-convention clause states the exemption. The docstring of the engine, `tools/gate_lint_language.py`, gives the host-masking detail, including which ASCII label can end a host.

## Shared spelling matcher (gate 2)
The language engine's public `spelling_matches(text, language)` runs the three spelling checks
(ise, isation and yse, after the URL and allowed-span masks) on one line or string literal. The
markdown scan, the generator-source scan and grc's CHANGELOG preflight aid
(`.claude/skills/corpus-management/tools/preflight-changelog.py`) all use it, so they share one
token matcher. The preflight judges each added line in isolation, so it can report a fenced
addition that the gate, which skips fenced blocks, does not.

## Normative wording
The `normative-wording` rule (`core/rules/normative-wording.md`) names the adopting library's quotation policy generically, because the pack is adoptable and has no mechanism that adapts a rule's text to an adopter. In grc the quotation policy is `NOTICE.md`, and the rule matches the requirement-language rule of the master project specification (section 6.1, rule 4) after that policy limited which sources may be quoted.

## Standards currency (gate 6)
The grc wrapper's module docstring (`.claude/skills/corpus-management/tools/lint-standards-currency.py`, "Exit codes") is the one authoritative list of each gate 6 exit status and every condition that produces it; this README does not repeat it. It names only the classes of exit: in report mode, only the legacy stale check's findings and a historical exception that does not bind block; a ratchet failure and malformed data in the tree exit 1; and unreadable or unsafe inputs, a base that cannot be determined or read, and malformed data at the base exit 2, apart from the exceptions the wrapper's exit-code list names. The standards-currency rule states the ratchet.

Until the earlier repository's 2026-10-20 change that read an explicit part or volume after a hyphenated SP number as part of the identity, the NIST grammar read the SP 800 series itself as an identity: "SP 800-series" and "SP 800-..." were read as "NIST SP 800", and "SP 800 series" as "NIST SP 800 series". All three now fall to the candidate inventory; a bare "NIST SP 800" still reads as the identity "NIST SP 800". In the earlier repository's 2026-10-27 change that read an allowlisted parenthesized programme name followed by a version as the citation's version ("NIST SP 800-218 (SSDF 1.1)" reads edition 1.1), one finding changed when measured over the corpus at main: the UNPINNED report for `dev-security/standard-jakarta-ee-application-security.md:269` was removed (UNPINNED 727 to 726 occurrences), and no other finding changed.

## Deliberately broad fence screens
Every engine that opens or closes a fenced region (the shared `aiqt_corpus.is_fence_line` toggle and the marker-aware parsers) reads a top-level backtick or tilde marker only after zero to three spaces of indent, as CommonMark does. The deliberately broad fence screens differ: each matches a fence-shaped line at any indentation, four or more columns or a tab included, and none decides which lines are fenced code. They are:

- the standards-currency sanction screen (`_simple_fences` in `tools/gate_lint_standards_currency.py`), a refusal screen that refuses any indented fence-shaped line (fail closed) rather than modelling it, and pairs column-1 fences only to decide whether to refuse the sanction;
- the loose-opener detector of the section 7.1 publisher source of record (`LOOSE_OPEN_RE` in `.claude/skills/corpus-management/tools/citation_publishers.py`, read by gates 101 and 102), which counts a fence-like line naming the `json citation-publishers` block at any indentation and in any fence style, so a second or non-canonical block cannot be silently ignored; every counted line fails loud (`InputError`: a count other than one, or a single counted opener that is not the exact canonical unindented one, parses nothing), and a regression test pins that a loose opener indented four or more columns, or by a tab, is still counted;
- the historical-citation register page screen (`.claude/skills/corpus-management/tools/historical_citation_register.py`), which refuses a page carrying a fence marker anywhere on a line outside its generated block;
- the operational-store example-delimiter screen (`STORE_EXAMPLE_DELIMITERS` in `.claude/skills/corpus-management/tools/lint_common.py`), which treats a fence or HTML-comment delimiter at any position in a line as making the surrounding structure uncertain; that only disables deferral (from the delimiter line to the end of the text it scans) and declaration (when the delimiter line is at or above the candidate header).

Each of these fails closed. In grc, the fence half of the canonical-matrix structure guard (`.claude/skills/corpus-management/tools/lint-matrix-control-codes.py`, also a refusal screen) uses the shared predicate and refuses an HTML block opener at any indentation. Container blocks (list items, block quotes) are not modelled by the toggle and marker-aware engines; the corpus-scan-integrity clause states the indent limit and that residue. The container-aware parsers (gate 104's `fenced_code_lines` and the gate-citation inventory's `_BlockScan`) measure the fence indent from the container's content column, as CommonMark does, so a marker at four or more columns can still open or close a fence inside a list item there.

## Index-header parity (gate 92)
The engine's `collect_findings()` (`tools/gate_lint_index_header_parity.py`) returns four values,
`(findings, warnings, rows_checked, title_worklist)`, or `None` when the index table's header row
is not found; `title_worklist` is empty unless the Title comparator is enabled. The grc wrapper
(`.claude/skills/corpus-management/tools/lint-index-header-parity.py`) is its only caller.
`check_row()` takes four optional keyword parameters, `col_title`, `title_field`, `title_baseline`
and `title_worklist_classes`; without `col_title` its result is unchanged. With them it compares the
stripped index and header titles exactly: an empty title on either side, a new difference, a pinned
pair whose titles changed, and a stale baseline entry whose titles now agree are findings; an
unchanged pinned pair passes, and one whose class is a work-list class is returned with a `DRIFT:`
prefix. `collect_findings()` takes the same options plus `title_classes` and
`title_baseline_partial`; with the Title option on, it validates each baseline entry (four
non-empty strings, a known class, titles that differ), reports a linked header with no title
field or a repeated one in the metadata head, reports a baseline entry that matched no readable
row (a warning when `title_baseline_partial` is set) and reports a run that compared no title.
The class names, the title field and the baseline stay project configuration.
Until the earlier repository's 2026-10-22 change that added the Title comparator, a linked document that was not
valid UTF-8 raised an uncaught `UnicodeDecodeError`; such a document is now a per-row finding
(`cannot read linked document`).

## Engine interfaces
The engines take project data as parameters or through `configure()`, so an adopter's wrapper
supplies its own catalogue, vocabulary or layout. The public interfaces and the behaviour an
adopter relies on are:

- **Profiles:** `tools/profile_loader.py` loads versioned TOML profiles from
  `defaults/grc/<concern>.toml`, registered in `core/profiles.toml`; an adopter overlay replaces
  values key by key, a malformed envelope fails closed, and regex tables are compiled on load.
  Gate 99 validates each declared profile as source; a profile is never an owned or generated file.
  The wrappers of gates 5, 19, 38 and 7 read the `citations`, `sections`, `placement` and `alignment`
  profiles; the engines of gates 2, 16, 12 and 9 take theirs through `run()`, as a
  `LanguageVocabulary`, a `StubVocabulary`, the `(pattern, label)` pairs of `placeholder_patterns()`
  and an `UncertaintyVocabulary`.
- **Gate 2 (language):** the three spelling checks are bounded by ASCII letters instead of `\b`,
  with case folding switched off inside the bounding class, so a word in `_` emphasis, in a
  snake_case name, or glued to a digit or a non-ASCII letter is reported; the URL scheme is matched
  as ASCII only. Known false positives: a code identifier that contains a checked word, and a word
  with a non-ASCII letter inside it, reported from after that letter. Known false negative: a
  non-ASCII character inside the checked part (a ligature, a soft hyphen, a zero-width space or a
  combining mark) can hide an `-ise` or `-yse` form, except that the patterns fold U+017F, U+0130,
  U+0131 and U+212A to `s`, `i`, `i` and `k`. The `ensure that` check uses the same bounds and
  exempts the verbatim external texts that the profile's `verbatim_ensure_titles` field lists. With
  `ise_prefixes` listed, `ise_words()` runs the prefixed pattern as a memoized linear-time search
  (the `ise_scan` field of `LanguageChecks`, `None` without prefixes).
- **Gate 6 (standards currency):** the public `identity_counts(report, kind)` returns one finding
  kind's occurrences per identity key; `ratchet(live, baseline)` compares two such maps, reading an
  omitted key as 0, and returns the identities whose live count is above (`over`) or below
  (`under`) the recorded one; `count_summary(report)` states the UNPINNED and UNREGISTERED totals
  (occurrences and distinct identities) on one line; and `print_coverage()` takes an optional
  `trailer` of lines that it prints in text mode just before the closing verdict line.
  `coverage_report` accepts wrapper-validated historical-context declarations (one path, one
  verbatim whole sentence, one registered superseded citation, a reason and evidence). A
  declaration binds only where its sentence stands as its own paragraph (a whole line from column
  1, blank lines around) on a non-code line; it masks for the legacy check only the one occurrence
  written exactly as the declared citation and is reported in a SANCTIONED inventory, and a
  declaration that does not bind is a blocking INVALID_EXCEPTION in every mode. A normalized stale
  occurrence is labelled BLOCKING only where a legacy pattern match starts at it and reports the
  same edition; another spelling or edition that the legacy check misses stays ADVISORY. The grc
  wrapper prints the totals on a `NOTE:` line and, on a default-scope run, holds each standard's
  UNPINNED count to the checked-in baseline
  `.claude/skills/corpus-management/tools/standards-currency-unpinned-baseline.json` and to its
  value at a base revision.
- **Gate 6 NIST grammar:** an explicit part or volume after a hyphenated SP number is part of the
  identity ("NIST SP 800-57 Part 1", "NIST SP 800-55 Vol. 1"), and `identity_key()` spells "Pt. 1"
  and "Pt 1" as "Part 1", and "Vol 2" and "Volume 2" as "Vol. 2"; a phrase that names no single
  part stays the bare identity. In the SP 800-63 family alone, a trailing "-N" is the publisher's
  revision ("NIST SP 800-63B-4" reads as identity "NIST SP 800-63B" at edition "Rev. 4"); only
  discovery reads that suffix, so a register row or bare exception is written without it. An
  allowlisted parenthesized programme name followed by a version is read as the citation's
  version: the allowlist (`PROGRAMME_VERSIONS`) has one entry, SSDF for NIST SP 800-218, read only
  when the name is written in capitals directly after that identifier and the version is N.N or
  N.N.N with the parenthesis closing directly after it. Any other programme name, such as
  "(SLSA 1.0)" or "(CMMC 2.0)", is not read as a version.
- **Gate 18 (intra-document references):** a line that names `ITSP.`, `ITSAP.`, `ITSG-`, `SPIN 20`
  or `Baseline Cyber Security Controls` (case-sensitive substrings, as for the ISO and NIST
  markers) cites an external framework, so its section marks are not checked; the issuer names
  CCCS, TBS and Treasury Board are not markers. Every section mark on a line naming GDPR, CPPA,
  PIPEDA, HIPAA, PCI DSS or SOC 2 (case-sensitive whole words) is external unless it is directly
  preceded by `see` (optionally `see also`) or directly followed by `above`, `below`, `here`,
  `herein`, `in this` plus one word, or `of this` plus one word. References and headings are
  compared at full numeric depth. Residual: an intra-document reference on a line that also names
  one of these instruments, or an uncued mark on a regime line, is not checked; line 104 of
  `security/standard-authentication-and-password-management.md` is one known instance.
- **Gate 62 (cross-file section references):** every line is split into cells on unescaped pipes
  outside matched code spans, and every cell is checked, so references in table cells are checked.
  The local-section exception applies only on a line whose first non-whitespace character is a
  pipe. Cross-file headings and cited references are cut to four levels, and an inline clause is a
  target section only at two to four levels.
- **Gate 22 (PII):** the public `is_citation_ip(line, start, end)` filter skips an IPv4-shaped match
  that is a four-part standard clause number cited directly after a section sign, "section",
  "sections", "clause", "clauses" or a standard designator (IEEE, ISO/IEC, ISO, IEC, NIST, SP or
  RFC, optionally followed by its document number), or later in a list of four-part clause numbers
  that one of these cues opens. A match followed by a port or a CIDR prefix length, or preceded in
  the same token by a URL scheme, is still reported, as is a bare address in prose. `scan` takes an
  `example_domains` keyword, so the example-domain allow-list stays wrapper configuration.
- **Gates 17 and 24:** gate 17's `scan` takes `repo_root` as a keyword for the finding's display
  path; gate 24's `scan` and `is_allowed` take an `allow_list` keyword, so the publisher allow-list
  stays wrapper configuration.
- **Gates 26 and 30:** gate 26 does not count a document's link to itself as an inbound reference.
  Gate 30's `scan_file` groups a run by the rendered paragraph, reading the block structure of the
  GFM specification version 0.29-gfm (block quotes, list items, fences, HTML blocks and tables, with
  its whitespace and blank-line rules), so an indented or lazy continuation line does not split a
  run; it reads a field name from its leading letter up to the colon, and it splits lines at
  newlines only. Residual: when a lazy continuation line that omits the markers of two or more
  nested block quotes is indented four or more columns and would start a block once unindented,
  the gate checks only the lines of its paragraph before that line, and no line from that line to
  the next blank line outside every container.
- **Gate 54 (NIST CSF control codes):** `codes_in()` returns each distinct code token in full.
  `check_code()` and `scan_file()` take two optional keyword predicates, `is_valid_subcategory` and
  `withdrawal_note`, and raise `TypeError` when `withdrawal_note` is given without
  `is_valid_subcategory`. With them, a suffixed code under a valid Category must be a live CSF 2.0
  Subcategory with exactly two ASCII digits; a withdrawn one is reported under
  `nist-withdrawn-subcategory` with its note, and any other under `nist-unknown-subcategory`.
  Without them, `scan_file()` stays at the Category level. Every dash punctuation (Pd) character of
  Unicode 16.0, plus U+2212, U+00AD and U+2043, is accepted as a hyphen; the set is a literal, and a
  regression test fails if the running interpreter knows a Pd character that the set lacks.
- **Gate 49 (matrix control codes):** `configure(ref)` takes five framework predicates
  (`is_valid_category`, `relocation_note`, `is_ccm_v41`, `is_aicm_only` and `check_iso_token`) and
  two optional AICPA TSC 2017 predicates (criterion membership and group-heading recognition). A
  table with the TSC column, recognized by its exact label, fails closed when they are not
  configured, a repeated TSC header is refused, and in every framework table a row whose cell
  count differs from its header is flagged.
- **Other `configure()` inputs:** gate 48's `configure(ref)` populates `VALID_DOMAINS`,
  `KNOWN_BAD_DOMAINS`, `CCM_V41`, `AICM_V11`, `ALL_TITLES` and `DOMAIN_NAMES` and rebuilds the
  structures derived from them. Gate 96's takes the valid-identifier union and the framework name,
  plus optional OWASP ASVS and MITRE CWE catalogues (ASVS as the union of every held edition, with
  `asvs_editions` naming them; ASVS identifiers are checked only in ASVS context), so a
  Privacy-Framework-only configuration is unchanged. Gate 100 takes
  `configure(directional_members)`; gate 73, `configure(objectives)`; gate 79, the SSDF practice and
  task catalogue; gate 47, the corpus layout (repository root, taxonomy path, register path and
  register section); gate 89, `configure(disclaimer)`; gate 88, the absolutes denylist and the
  external-standard citation vocabulary; gate 87, the narrative root and its two mention regexes;
  gate 86, the narrative document type, the entry-point exemption, the 7-field extension set, the
  allowed corpus document types and the two marker regexes; and gate 84, ten project-content sets.
- **Gate 73 (COBIT titles):** besides Manage, Managed, Ensure and Ensured, which match
  case-insensitively, a title may open with Managing, Ensuring or the Monitor, Evaluate, Assess,
  Deliver, Align, Build and Direct families in their listed capitalization. `extract_title` takes a
  `quote` argument, which `scan_text` fills when a quote precedes the code. The rule and its
  generated reference list the residuals and the known false positives.
- **Gates 67 and 82:** gate 67's `collect_findings` fills wrapper-supplied message templates (a
  `{tokens}` slot) and hard-codes no project schema word. Gate 82's `run` takes an optional `scan`
  reader, so a wrapper can read its declared text scope through its own strict reader.
- **Compiler and skill:** the `corpus-management-skill` file-kind generation rule renders
  `core/skill/SKILL.md` verbatim to `.claude/skills/corpus-management/SKILL.md` with
  `provenance = false`, because a skill's discovery frontmatter must start at line 1; the
  generated-from note is in the body. The rule index is generated to
  `.claude/skills/corpus-management/rule-index.md`, and gate 37 reports an index-kind ownership
  entry anywhere under `.claude/rules/`.

## Release versioning
Gate 99's `--release-delta` mode (`tools/pack_release_delta.py`) checks the manifest version
against every change to a pack file, README files included. Every change must have at least a PATCH
bump; added identifiers, clauses, public functions, `configure()` inputs or literal accepted-key
declarations (at module level or in public classes and functions) must have a MINOR; their removal
must have a MAJOR (a MINOR while the major version is 0). Keys accepted in other ways, and
breaking-shaped edits the rules do not name, count as PATCH. A maintainer-approved row in
`core/release-waivers.toml` can waive one exact upward transition. When the mode was added in the
