## 1. F1 (warning). The applied W1 fix can retire a genuinely outstanding order

The applied implementation collects `delivered` = every `.md` file in every `outbox/<worker>/` across
all families, then in `merge_orders`:

```python
for oid in delivered:
    merged.pop(oid, None)
```

**The order asks what happens when the same id sits in an outbox AND in available-work. It vanishes.**
Measured directly against the merged code:

```text
case                                                          applied
order X pending in available-work AND present in an outbox     RETIRED (dropped from the count)
order X claimed in an inbox AND present in an outbox           RETIRED
control: pending with no outbox file                           {'X': 'pending'}
```

With one live worker, retiring a genuine pending order moves the verdict from `SATURATED` to
`IDLE-CAPACITY`. That is the under-count direction, and while it is the less dangerous of the two
(it prompts fan-out rather than suppressing it), it makes a genuinely outstanding order **invisible to
the observable**, which is how an order gets forgotten.

**The precondition is live right now, not hypothetical.** A NOT-RUN notice is an outbox file for work
that was never done: `opus/outbox/opus-20260725T040036Z-d268/validate-pr-1153.md` exists and its
verdict line reads `NOT RUN`. The work still needs doing. If the orchestrator re-dispatches
`validate-pr-1153` under the same id (the natural move, since the id names the work), the saturation
tool will not count it.

**What saves it today is a convention, not the code.** The orchestrator's observed practice is to
RENAME on re-issue: `ha-h01-falsepos` became `ha-h01-falsepos-2`, `verify-1156-prepush` became
`verify-1156-small`. Both avoided the collision by accident of naming rather than by design. A
same-id re-dispatch is not forbidden anywhere.

**Fix, verified, one line.** Retire only ids that file-drop does not currently show as live:

```python
for oid in delivered - set(filedrop_orders):
    merged.pop(oid, None)
```

Tested against all four cases:

```text
case                                                          applied     proposed
the W1 phantom (scratch pending, delivered, absent file-drop)  retired     retired      <- still fixed
re-dispatched (pending on file-drop AND an old outbox file)    retired     pending      <- corrected
claimed on file-drop AND an old outbox file                    retired     claimed      <- corrected
ordinary pending, no outbox                                    pending     pending      <- unchanged
```

It keeps the W1 fix exactly (a scratch-only phantom has no file-drop entry, so it is still retired) and
never retires an order file-drop currently shows. The evidence-is-delivery principle the docstring
states is preserved; the change is only that current file-drop presence outranks a historical outbox
file, which is the same "later state wins" logic `merge_orders` already applies to claimed-over-pending.

### Can a delivered id be MISSED, so the phantom survives?

Three ways, all narrow:

- **An unreadable outbox directory (F3).** `_entries` returns `([], False)`, the path is appended to
  `unreadable`, and no delivered ids are collected from it, so any phantom it would have retired
  survives. **Not silent**, since the unreadable path is reported, which is the behaviour the #1157
  change added for exactly this class. Note-level.
- **A result file with a non-`.md` suffix.** Deliveries always write `<id>.md`, so this is theoretical.
- **A nested result** (`outbox/<worker>/<subdir>/<id>.md`). `_entries` is non-recursive. Not a current
  shape.

### F2 (note). A NOT-RUN notice reads as a delivery

`delivered.add(_order_id(p))` accepts any `.md` in an outbox, so a NOT-RUN notice, a declined order,
and a completed result are indistinguishable. For the phantom purpose this is arguably right: the
git-scratch row should not sit `pending` forever once a worker has responded. But the set is named
`delivered` and the docstring says such an order "is FINISHED", which a NOT-RUN notice is not. **Failure
scenario:** a reader (or a future change) treats `delivered` as "work completed" and builds on it, when
it means "a worker wrote something back". Worth one clarifying clause, and it is the same conflation
that makes F1 reachable.
