### F2 (ERROR) The self-test count in code is hardcoded and wrong, and the CHANGELOG repeats it

- **path:line:** `tools/audit-inbox-drops.py:172` and
  `.working/changelog-details/CHANGELOG-detailed.md:19` ("Self-test 6/6, including that case.").
- **Axis:** (a), a CHANGELOG claim about what a tool does, checked against the code rather than
  the docstring.
- **Evidence.** The self-test calls `check()` **seven** times: a real drop is unprocessed; a
  `.diff` is staging; a `.log` is staging; README is ignored; archived drops are counted; age
  does not mark a drop processed; an absent drop dir is a no-op. Running it prints **seven PASS
  lines** and then `self-test: 6/6 passed`, because line 172 is
  `print(f"\nself-test: {6 - len(failures)}/6 passed" ...)` with the denominator as a literal.
- **Failure scenario.** Both numerator and denominator are decoupled from the actual check
  count, so a future eighth check is silently absent from the reported total, and a reader
  auditing coverage from the tool's own output under-counts it. The pass/fail verdict itself is
  unaffected (the failure branch prints `FAILED (n)` and returns 1), so this is a reporting
  defect, not a false green. It is error-severity because a stated verification count is the
  thing being relied on and it is wrong in both the code and the CHANGELOG.
- **Fix shape.** Count the checks (`total` incremented inside `check`) and print
  `{total - len(failures)}/{total}`, then correct the CHANGELOG to 7.
- **Note in fairness:** the sibling tool in this PR does this correctly. My run of
  `tools/audit-worker-saturation.py --self-test` reports `24/24`, computed from summed
  case counts, and that number moved from 23 to 24 with this PR's added case.

### F3 (WARNING) A worker can corrupt the audit log that is this tool's only accountability record

- **path:line:** `tools/manage-workers.py:158` (the log row f-string), with the value sourced at
  `tools/manage-workers.py:131` (`held[wdir.name] = p.stem`).
- **Evidence, demonstrated rather than reasoned.** The `held` value is interpolated **unescaped**
  into a markdown table row. It is derived from an order file's NAME in
  `<root>/<family>/inbox/<worker>/`, and that directory is group-writable (`drwxrws---`, group
  `grc`) with the worker's own account in that group, which the transport requires because
  `claim` and `deliver` write there. In a throwaway tree (the live exchange was NOT touched), a
  file named with embedded pipe characters produced:

```text
| 2026-07-25T14:20:34Z | <session> | claude | wake | zz | FORGED | x | reason | `/credit-offload` |
   pipes in row: 10   (a well-formed row has 8)
```

  Two extra columns, and every field after the held-order column shifts: the reason lands in the
  keys-sent column. I also confirmed the adversarial value can WIN over a genuine order file:
  `held_orders` assigns `held[wdir.name]` once per matching file in a loop, so the last one
  iterated wins, and in two of three arrangements I tried the adversarial name was the one that
  reached the log.
- **Why it matters.** The tool's stated justification is that "Keystroke injection into a
  session running as another user is invisible unless recorded", so the log's integrity IS the
  control. A worker able to inject arbitrary text into the row recording an action taken
  against it can corrupt or obscure that record.
- **Scope, stated precisely so this does not read as more than it is.** This is **not** prompt
  injection, and the PR's headline safety claim is sound: I verified that the keystroke path
  reads only literal constants from `VERBS`, so no worker-influenced value reaches
  `tmux send-keys`. The exposure is confined to the log row.
- **Fix shape.** Escape or strip `|` and newlines from `held` (and from `reason`, which is
  orchestrator-supplied and so only a self-inflicted risk) before writing the row; or write the
  log as one fenced block per send rather than a table.
- **Secondary defect at the same site.** Because `held[wdir.name]` is overwritten per file,
  a worker inbox holding two order files logs only one of them, while the destructive-verb gate
  at line 206 correctly blocks on any. So the gate and the record disagree about a
  two-orders-in-one-inbox state, which is exactly the anomaly the sibling saturation tool
  deliberately preserves rather than collapsing.

### F4 (WARNING) A concurrent drop consumption crashes a tool documented never to exit non-zero

- **path:line:** `tools/audit-inbox-drops.py:117` (`kb = p.stat().st_size / 1024.0`), against
  the docstring claim at `tools/audit-inbox-drops.py:28` ("every reporting path exits 0").
- **Evidence.** `age_days()` at line 65 guards `p.stat()` with `try/except OSError`, and line 117
  does not. The path list is built in `survey()` and consumed later in `report()`, so there is a
  window between them.
- **Failure scenario.** The orchestrator processes a drop (moving it to `done/drops/<YYYY-MM>/`)
  while the report loop is between `survey()` and line 117. `p.stat()` raises
  `FileNotFoundError`, the tool exits with a traceback and a non-zero status, and the docstring's
  guarantee is broken. This is not hypothetical scheduling: the tool is wired into the statusline
  (so it runs on every refresh) and into `/resume` step 3, and processing drops is exactly what
  the orchestrator does at those moments.
- **Fix shape.** Reuse the guarded pattern: a `size_kb(p)` helper returning 0.0 on `OSError`, or
  wrap the loop body.

### F5 (WARNING) A genuine drop with a staging-shaped suffix is reported as not awaiting a read

- **path:line:** `tools/audit-inbox-drops.py:47` (`TRANSIENT_SUFFIXES = (".diff", ".patch",
  ".log", ".tmp")`), with the docstring's claim at line 22 that this trap is avoided.
- **Evidence and failure scenario.** Classification is purely by filename suffix and prefix. A
  maintainer or worker drop named `deep-assessment.log`, or any `.diff`/`.patch` a worker
  delivers as design input, is put in the staging bucket and reported under "STAGING
  (orchestrator scratch, **not work awaiting a read**)". The originating incident was a 13KB
  external assessment; had it arrived with a `.log` suffix, this tool would have mis-classified
  the exact artefact it was built to surface.
- **Mitigating, and why this is warning and not error:** staging items ARE still printed, so the
  drop is visible; only its STATUS is wrong. The `--oneline` statusline form, however, reports
  staging in a separate counter and the suppression is keyed on the unprocessed count, so a
  mis-classified drop **is** suppressed from the statusline entirely.
- **Fix shape.** Either narrow the rule to the prefixes only (which are orchestrator-controlled
  and intentional) and drop the suffix heuristic, or state in the report that a staging
  classification is a filename guess and list the bucket in the `--oneline` form when non-zero.
