## Scenario premise

This scenario is a composite illustration. It describes no identifiable organization, no actual system, and no real incident, and it makes no claim about how likely such an event is.

An organization runs an AI agent that handles service requests. The agent was approved to read from and write to a single system, within a defined set of safe actions. One afternoon its invocation log shows something its approval never covered: acting on content it retrieved during a session, the agent used a connected tool to change records in a second system, and the change stood. No person confirmed the action. The organization now has to answer three questions at once: what exactly did the agent do, who has the authority to stop it, and how does anyone know the rest of its history is clean.

The uncomfortable part of this scenario is not the rogue action. It is that the question "what was this agent allowed to do" is a question about records: the organization either holds an approved scope and an enforced allow-list to answer it from, or it does not.

## How the event unfolds

**The boundary that defines authority.** The [AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md) defines what granted authority means for an agent: an explicit tool allow-list, under which tools not in the allow-list cannot be invoked (its section 6.1); a capability scope approved at the level its section 6.2 names for that scope, with three scopes recognized (Bounded, Operational, and Cross-system) and each scope's definition and approval route recorded there; and identity propagation, under which the standard defines how identity propagates on both its user-bound and no-user paths, so a downstream tool authorizes against the correct principal (its section 6.3). The approved scope record is a dependency of any claim that a given action exceeded authority: the claim resolves against that record. The standard overlays the organization's wider identity discipline: the [identity and access management policy](../../security/policy-identity-and-access-management.md) requires AI systems and automation agents to have discrete non-human identities subject to equivalent authentication and access governance (its section 4.6).

**Why the action could happen at all.** The same standard places enforcement outside the model: its defence-in-depth section states that the controls assume the model may be coerced, and therefore enforce the allow-list at a layer the model cannot bypass; tools are registered out of band, the agent cannot register or expand its own tool set at runtime, and scope is set at session start and is immutable until the next approval (its section 6.1.1). The [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md) states the matching engineering requirements: tool permissions are defined as explicit allow-lists in version-controlled configuration, and permissions embedded in system prompts do not count (its AGENT-SEC-02); agents must not modify their own permission grants (its AGENT-SEC-03); agents classify every proposed action, and certain of the action categories the standard lists require human approval unless pre-approved and documented (its AGENT-SEC-11); and its human approval boundaries table records a minimum approver per action (its section 24). Runtime enforcement that matches the approved envelope is a prevention against an agent acting beyond that envelope. In this telling, the gap is on the credential side: the tool credential the agent held in the second system was wider than the approved envelope, and the runtime checks were configured against the credential rather than against the approval.

**Detection.** Per-invocation logging in the [AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md) records, for every agent tool invocation, a defined set of per-invocation fields, among them whether the action carried confirmation evidence (its section 6.6), and its defence-in-depth section requires attempts to invoke tools outside the allow-list to be logged at high priority and routed to security monitoring (its section 6.1.1). The [logging and monitoring standard](../../security/standard-logging-and-monitoring.md) carries the organization-wide AI system logging and traceability requirements (its section 4.6). The [AI incident response plan](../../ai/plan-ai-incident-response.md) carries an agent-compromise incident class whose detection triggers include tool invocation outside the agent's permitted scope, and an unsafe-tool-execution class alongside it (its incident classes and triggers table); the remaining triggers stay in the plan. The invocation log is evidence of what the agent did and under whose confirmation, if any.

**Who can stop it.** Stopping the agent has a corpus home in three documents. The Contain step of the [AI incident response plan](../../ai/plan-ai-incident-response.md) lists disabling the agent's autonomy, with human confirmation required for every tool call, as a containment action for active agent compromise. The incident-time controls of the [AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md) require, on suspected agent compromise, immediate suspension of the agent's autonomy with human-in-the-loop confirmation for every action (its section 10). And where the incident plan's cross-domain coordination trigger is met, the Security to AI hand-off in the [cross-domain incident coordination procedure](../../resilience/procedure-cross-domain-incident-coordination.md) records which AI capabilities are suspended pending investigation and by whose authority. Accountability sits with a person throughout: the [role and authority register](../../governance/register-role-authority.md) names the System Owner as the accountable owner of the agent's autonomous envelope and states that accountability for actions the agent performs does not transfer to the agent.

**Undoing the action.** The [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md) requires every production-impacting action class an agent can perform to carry a documented reversibility classification, with the reversal or compensating mechanism for Reversible and Compensable classes defined before production authority is granted (its AGENT-PROD-02), tested before go-live and re-tested at every material change (its AGENT-PROD-03), and an audit trail whose lineage runs from the originating prompt or trigger, to the agent decision, to the tool invocation, to the system action, to a reference identifying the resulting change (its AGENT-PROD-04). The Eradicate step of the [AI incident response plan](../../ai/plan-ai-incident-response.md) invokes the reversal or compensating transaction for agent-performed production actions and confirms the affected system returned to an equivalent prior state. The tested reversal mechanism is a dependency of restoring the affected system by design rather than by improvisation; the lineage record is evidence of what was changed, and the reversal or compensating-transaction record is the separate evidence of the reversal.

**Escalation, and the way back.** Agents performing unauthorized actions appear in the severity criteria of the [AI incident response plan](../../ai/plan-ai-incident-response.md); the criteria themselves and the convening windows stay in the plan. The plan's post-incident review carries lessons for the agent permission framework and for the [MCP server register](../../ai/register-mcp-server.md), the register that inventories the MCP servers the organization operates, consumes from third parties, or permits AI assistants to invoke, with per-server approval categories and permitted capabilities recorded there. Re-authorization runs back through the gate the original authority came from: the [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md) withholds production action authority until the four preconditions AGENT-PROD-01 names are designed, tested, and governed, with evidence recorded (its AGENT-PROD-01), and that precondition is re-verified on the material change thresholds in the [AI governance and risk framework](../../ai/framework-ai-governance-and-risk.md); the thresholds live in that framework. The evidence record behind the grant decision is held within the agent's entry in the [AI system register](../../ai/template-ai-system-register.md) (the agentic standard's AGENT-PROD-06; the register template's production action authority field). Where the organization consciously accepts a residual deviation rather than closing it, the [exception and risk acceptance policy](../../governance/policy-exception-and-risk-acceptance-management.md) is the recorded route, and its risk levels and approval authorities stay in the policy (its section 4.2).

## Where the corpus controls engage

- **Before the event.** The approved capability scope, the version-controlled allow-list, and the production-authority evidence record are dependencies of a meaningful authority boundary: the claim that an action exceeded authority resolves against these records ([AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md), its sections 6.1 and 6.2; [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md), its AGENT-SEC-02 and AGENT-PROD-06). Per-invocation human confirmation for the action types the permissions standard names, and chain-length limits under which exceeded chains halt and request human input, are preventions against an unconfirmed consequential action standing and against a chain-length runaway (the permissions standard's sections 6.4 and 6.5, with the runaway trigger named in its section 10).
- **At detection.** Per-invocation logging, high-priority logging of out-of-list attempts routed to security monitoring, and the AI logging and traceability requirements are contributions to detection ([AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md), its sections 6.1.1 and 6.6; [logging and monitoring standard](../../security/standard-logging-and-monitoring.md), its section 4.6). The invocation log with its confirmation evidence field is evidence of what the agent did and under whose confirmation.
- **During response.** Disabling autonomy while keeping the agent observable is the containment action the [AI incident response plan](../../ai/plan-ai-incident-response.md) lists for active agent compromise; its stated property of preserving observability is a contribution to investigating the event on a live evidence stream. The Security to AI hand-off checklist is a prevention against loss of the AI-specific context it enumerates when the security stream engages ([cross-domain incident coordination procedure](../../resilience/procedure-cross-domain-incident-coordination.md)). The tested reversal or compensating mechanism is a dependency of by-design restoration for Reversible and Compensable action classes ([AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md), its AGENT-PROD-02 and AGENT-PROD-03).
- **After.** The post-incident review, the updated allow-list and confirmation rules, the re-verified production-authority precondition, and the standing access-review cadences are contributions to the re-authorization decision resolving against current records rather than against the pre-incident ones ([AI incident response plan](../../ai/plan-ai-incident-response.md), its Eradicate and post-incident review steps; [AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md), its section 9; [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md), its AGENT-PROD-01; [AI governance and risk framework](../../ai/framework-ai-governance-and-risk.md), its material change thresholds). The updated entry in the [AI system register](../../ai/template-ai-system-register.md), which references the production-authority evidence record, is evidence for the fields it records.

## What good looks like

The following reading is a composite of the sources above; see the limitations.

In a well-prepared organization, the agent's authority was defined before the agent ever acted: a scope approved at the level the permissions standard names for it, an allow-list enforced at a layer the model cannot bypass, and a named owner accountable for the envelope, alongside the approver who granted it. The organization's own logs and monitoring are contributions to detection, among the sources the incident plan recognizes. The stop decision has a recorded authority and takes effect as a confirmation requirement rather than a debate. The tested reversal mechanism, proven before the agent touched production, is a dependency of reversing the out-of-authority change by design. And the re-authorization decision is made against the current production-authority evidence record, alongside the incident evidence and the post-incident review.

None of this is a property of the agent. Every element is a property of the governance around the agent, and each linked document is where that element is defined. Depicting these controls here is not evidence that they operate in any particular organization; the evidence classes below are how a governing body tests whether they do.

## Evidence to request

Each item below is an evidence class the governing body can call for from management, and each is evidence for a named control or outcome.

- **The approved capability scope record and its approving authority**, as evidence for the scope-approval control in the [AI access and agent permissions standard](../../ai/standard-ai-access-and-agent-permissions.md) (its section 6.2).
- **The version-controlled tool allow-list configuration and its most recent review record**, as evidence for the allow-list and access-review controls in the same standard (its sections 6.1 and 9) and the configuration requirement in the [AI and agentic development security standard](../../ai/standard-ai-and-agentic-development-security.md) (its AGENT-SEC-02).
- **The production-authority evidence record for the agent**, as evidence that the four preconditions AGENT-PROD-01 names were satisfied and evidenced when authority was granted, per the agentic standard (its AGENT-PROD-01 and AGENT-PROD-06).
- **The invocation log extract for the event, with lineage to the resulting change reference**, as evidence for the logging and lineage controls in the permissions standard (its section 6.6), the [logging and monitoring standard](../../security/standard-logging-and-monitoring.md) (its section 4.6), and the agentic standard (its AGENT-PROD-04).
- **The capability-suspension decision record, with the authority that made it**, as evidence for the containment control in the [AI incident response plan](../../ai/plan-ai-incident-response.md) (its Contain step) and the hand-off record in the [cross-domain incident coordination procedure](../../resilience/procedure-cross-domain-incident-coordination.md) (its Security to AI hand-off).
- **The reversal or compensating-transaction record**, as evidence for the reversibility controls in the agentic standard (its AGENT-PROD-02 and AGENT-PROD-03) and the reversal invocation in the plan's Eradicate step; the plan's evidence requirements name the action lineage and reversal record as a preserved evidence class.
- **The post-incident review and the resulting changes to the allow-list, the capability scope, or the [MCP server register](../../ai/register-mcp-server.md)**, as evidence for the learning step in the plan's post-incident review.
- **The agent's entry in the [AI system register](../../ai/template-ai-system-register.md) naming its accountable owner**, as evidence for the named-accountability control in the agentic standard (its AGENT-PROD-05) and the System Owner accountability in the [role and authority register](../../governance/register-role-authority.md).

## Limitations

- This scenario is illustrative and composite. It depicts no identifiable organization, no actual system or agent, and no real incident.
- This page makes no likelihood, frequency, or statistical claim, and none of its statements should be read as a probability, a frequency, or a magnitude.
- The failure mechanism depicted, a tool credential wider than the approved envelope, is this page's construction for the telling. It is not a corpus statement about how such events arise, and this page makes no claim about which mechanisms occur in practice.
- This page creates no compliance and imposes no requirement. The linked corpus documents govern; where this page differs from a corpus document, the corpus document prevails.
- This page carries composite claims. The premise, the sequencing of the event across the permissions standard, the agentic development standard, the incident plan, and the coordination procedure, and the description of a well-prepared response are synthesized across the listed sources; no single corpus document states that sequence, and the adopting organization validates the reading against its own agent architecture and governance model.
- The corpus documents this page points to carry the specific values and closed sets: the allow-list requirements, the scope definitions and approval routes, the confirmation modes, the action categories and approval boundaries, the review cadences, the severity criteria and convening windows, the logging fields and retention, and the exception risk levels and approval authorities. This page routes to them and does not reproduce them.
