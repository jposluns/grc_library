## 1. Purpose

This specification defines the GRC Documentation Library's automated audit programme: the set of machine-checked rules that gate every change to the library, the mechanisms by which the rules are enforced, the surfaces on which they run, and the conditions under which gates are added, modified, or retired.

The audit programme is the library's primary defence against the failure modes catalogued in [`governance/specification-citation-verification.md`](specification-citation-verification.md) §5: drift, contradiction, mis-attribution, stale references, and silent regressions in document structure, naming, and cross-linkage. Where the Citation Verification Specification governs *what is true about the world* (publisher metadata about external standards), this specification governs *what is internally consistent about the library itself*.

- Manual quality reviews (governed by [`governance/procedure-library-quality-and-review-cadence.md`](procedure-library-quality-and-review-cadence.md)).

## 3. Design principles

The audit programme rests on five principles:

1. **Determinism over heuristic**. Every gate produces a deterministic pass/fail outcome. No gate depends on network access or third-party services. The result is a function of the repository state alone, with one bounded exception: the date-sensitive gates, which compare a repository-recorded date field against the current date (per-document date staleness and review cadence, citation and tooling currency and freshness, and follow-up ageing, plus the advisory daily-changelog-rollup check). The current date is their only external input, and each is otherwise deterministic from repository state.
2. **Stdlib-only Python (one sanctioned exception)**. Every linter is implemented in Python 3.11 standard-library code, with a single sanctioned third-party dependency: `idna` (allow-listed in gate 71, pinned in `requirements.txt`, installed in CI), used for exact UTS-46 domain-label validity in the PII gate (gate 22) and imported soft-optional with a stdlib fallback, so a bare interpreter still runs every gate. This keeps the audit programme reproducible across local, CI, and pre-commit surfaces with a Python interpreter plus the single pinned dependency.
3. **One gate, one concern**. Each gate enforces a single, narrowly defined rule. Failure messages name the rule, the file, the line, and the offending content. When a rule's domain grows beyond one file, the gate is split rather than overloaded.
4. **Conservative scope over false positives**. A gate that would produce legitimate false positives at scale is scoped narrowly to what it can track without false positives, or not shipped at all. (An earlier variant kept a deliberately dormant pattern as forward scaffolding, for example [`tools/lint-cross-doc-numbers.py`](../tools/lint-cross-doc-numbers.py)'s P1/P2/P3-acknowledgement patterns from Phase 23.26; that scaffold was retired per the deep-assessment r3 DA-gate25-scaffold finding because a permanently zero-tracking pattern adds no protection while implying coverage the gate does not provide, so dormant scaffolding is no longer kept. The gate stays active on its GDPR-breach-notification term.) Honest scope management is preferred over either silent false positives or blanket exemption lists. A permitted exception is *meta-documents* whose purpose is to describe a linter's rule set (the linter script itself, the CHANGELOG, this specification, and the Citation Verification Specification): these documents inevitably contain the patterns the linter searches for and are exempted by name in the linter's exemption list, with an inline comment naming the reason.
5. **CI parity**. The local audit runner and the pre-commit hook always run the same set of gates as the CI workflow. Drift between the three surfaces is itself a recoverable defect rather than a feature.

## 4. Enforcement surfaces

The same audit-gate set runs on three surfaces:

| Surface | File | Invocation | Blocking? |
| --- | --- | --- | --- |
| GitHub Actions | [`.github/workflows/quality.yml`](../.github/workflows/quality.yml) | Automatic on push and pull-request events | Yes; required check for merge |
| Local audit runner | [`tools/run_all_audits.sh`](../tools/run_all_audits.sh) | `tools/run_all_audits.sh` (or `FAIL_FAST=1 ...`) | Yes by convention; the maintainer does not push without all gates green |
| Pre-commit hook | [`.pre-commit-config.yaml`](../.pre-commit-config.yaml) | `pre-commit install` (one-time setup); automatic on `git commit` | Yes; commit blocked on failure |

Of the three surfaces, only the GitHub Actions workflow is authoritative: a green CI run is the only signal a reviewer can rely on. The local runner and pre-commit hook exist to catch failures earlier in the loop so they never reach CI. When the three surfaces diverge, the workflow is the source of truth and the others are synchronized to it.

Gates 43, 45, 46, 50, 51, 59, 60, 63, 78, 81, 90 and 107 and delta gate D14 resolve ledgers, backlog identifiers or history rows against the private store (the operational store or the `grc_library_private` sibling); when it is absent, as in public CI and adopter clones, each skips the dependent checks without changing its exit status, and prints a line beginning `DEGRADED:` naming what it skipped whenever it skips a check because the store is absent, so a green CI run of those gates attests nothing about the skipped checks. Gates 43, 78, 81 and 90 print the line only on their default lookup, not when `--root` or explicit paths name their input; under `--root`, gates 78, 81 and 90 read no private sibling and take their private input from the root (gate 90 from `--private-root` when given), and gate 107 prints it only when it skips at least one reference. When the environment variable `GITHUB_ACTIONS` is `true`, the shared helper in `tools/lint_common.py` that prints the line also prints it as a GitHub Actions warning annotation (a line beginning `::warning title=<gate> degraded::`), so it shows on the run summary rather than only inside a collapsed green step. The local runner (`tools/run_all_audits.sh`) is unchanged and shows neither line for a passing gate; the maintainer runs it with the store present, where no gate degrades, but the nightly-sweep workflow also runs it in GitHub Actions without the store, and there neither line of a passing gate is shown.

Gate 48 is a CSA CCM/AICM citation-accuracy audit: it loads the authoritative control reference in [`tools/ccm_aicm_reference.py`](../tools/ccm_aicm_reference.py) (a fair-use citation index of domain codes, control-ID ranges, and canonical control titles derived from the CSA-published CCM v4.1.0 and AICM v1.1.0 catalogues, carrying none of those catalogues' normative content, so it is an index rather than a redistribution of the matrices) and checks seven things across the corpus. First, **code validity**: every `<DOMAIN>-<NN>` token whose domain is in the CCM/AICM family must name a real domain and an in-range control number (catching superseded or fabricated domains such as `IVS` (renamed to `I&S` in v4.1.0), `GRM` (the v3.0.1 governance code), `GOV` and `NET` (which do not exist), and out-of-range control numbers, such as an `IPY` control above the domain's fourth). Second, **title match** (control-listing tables only): a row (`| <CODE> | <title> |`) whose cited title shares no content word with the catalogue title is flagged as mis-attributed; the lookup is section-aware (a row under a `## CSA CCM ...` heading is checked against the CCM v4.1.0 title, one under a `## AICM ...` heading against the AICM v1.1.0 title, and one under neither against the AICM-wins union), and the check is deliberately conservative, tolerating the corpus's localized and abbreviated titles while catching fabricated ones. Third, **cross-catalogue title** (rows under a CCM/AICM section): a small set of controls share a code across both matrices but carry titles differing by a distinctive content word (I&S-07 is "Migration to Cloud Environments" in CCM v4.1.0 but "Migration to Hosted Environments" in AICM v1.1.0), which the conservative content-word check above cannot catch because the two titles share most words; this check fails a row under a CCM section that carries the AICM variant's distinctive word (and none of the CCM variant's), and vice versa. Fourth, **bare domain code** (CCM/CSA-context lines): a superseded or fabricated domain code cited as a bare token with no `-NN` suffix (a framework family list, a domain-keyed crosswalk row, a glossary-style entry) carries nothing for the code-validity check to see, so this check flags such a bare known-bad code when the line either names the matrices (CCM / CSA / Cloud Controls Matrix / AICM) or sits under a CCM/AICM section heading and is not a historical rename-note; it is precision-first (a bad code in an unlabelled multi-framework row under a generic heading is left for the apply-time grep and the periodic sweep). Fifth, **framework-as-column family** (framework-alignment tables with a CSA CCM / AICM column): the code-validity check policies only tokens whose prefix it recognizes as a CCM/AICM family (valid or known-bad), so an invented family prefix that no matrix defines (`END`, where endpoints are `UEM`; `ISM`; `GVN`, where governance is `GRC`) is silently skipped even when cited in a column explicitly headed `CSA CCM v4.1` or `AICM`; this check, scoped to that named column only, flags any control-code-shaped token there whose domain prefix is outside the CCM/AICM family as an unknown family (the deep-assessment r1 R11 discovery, closing the blind spot the `ISM`, `END`, and `GVN` invented families exposed; a NIST or ISO code in a non-CCM column is untouched, and known-bad domains stay with the code-validity check, so there is no double-flag). Sixth, **framework-label-row title** (framework-alignment tables whose rows name the framework in a cell rather than in a column header): where a row carries its framework label in one cell and the code plus title in the NEXT cell (`| CSA CCM v4.1 | GRC-01 <title> |`), the code and title never reach the title-match check above, which expects the code in the row's first cell; this check flags a cited title that shares no content word with the catalogue control title (the Sweep-129 GRC-01 class, GRC-01 "Governance Program" cited as "Risk Management Framework"), with an exemption for the legitimate cite-the-domain convention: a title that renders the code's DOMAIN name is exempt when more than half its content words appear in that domain name (the source-verified `DOMAIN_NAMES` map), measured on the base title before a trailing ": qualifier": IAM-15 "Identity and Access Management: PAM" is exempt on its base "Identity and Access Management" (all three words in the IAM domain "Identity & Access Management") while GRC-01 "Risk Management Framework" (one of three base words in the GRC domain "Governance, Risk and Compliance") still flags (maintainer-decided 2026-08-01). The check is precision-first: a cell carrying two or more codes is skipped, and the more-than-half heuristic is deliberately lenient (a documented false-negative residual on a wrong title whose words are mostly domain words; a per-domain reviewed-alias table is the tighter alternative). Seventh, **bare-domain inline title** (code-first colon or parenthetical forms in explicit CCM/AICM context, or a CSA-labelled column's leading domain-plus-title value): a citation that gives a valid bare domain code with no `-NN` control number followed by an inline title, which the numbered title checks cannot see (there is no `<DOMAIN>-<NN>` token, for example `SEF: Software Engineering and Development`), is flagged when that title matches neither the domain's own name nor a uniquely best-resolving control title in the domain (a title fabricated on a bare domain code), judged by the same greater-than-half content-word threshold as the sixth check (PR #1336, the Sweep-1329 class). Gate 73 is a COBIT 2019 objective title-text audit (PR #1074): where a corpus document pairs a COBIT objective code with a recognized verb-led, title-shaped phrase, that phrase is validated against the canonical COBIT 2019 objective title encoded in [`tools/cobit_iso31000_reference.py`](../tools/cobit_iso31000_reference.py) (`COBIT_OBJECTIVES`, the 40 governance and management objective titles), and any divergence is a finding. It closes the OBJECTIVE-title half of the gap gate 61 leaves open: gate 61 validates COBIT code EXISTENCE and the ISO 31000 designation but deliberately not citation TITLES, and the practice titles line-wrap in the held extract so they stay unchecked (only the objective titles extract cleanly). The motivating defect class (a validate-pr-987 note) is the imperative verb form `DSS05 Manage Security Services` where the canonical COBIT 2019 title is the past-participle `Managed Security Services` (the EDM domain uses the `Ensured` participle), and a truncated title (`DSS02 Manage Service Requests` for the canonical `Managed Service Requests and Incidents`) is the same finding. It is precision-first: a code is checked for a title ONLY when a canonical-title-shaped phrase immediately follows it (after an optional code wrapper (`**`, `__` or backtick), whitespace and one optional separator (colon, hyphen, en dash, em dash, pipe, quote, opening parenthesis, comma, semicolon, slash or opening bracket), the next word is one of the forms listed below; only the first two forms in each of the Managed and Ensured families match case-insensitively, while all other forms require the listed capitalization; a candidate must contain at least two words before the field boundary), so a code cited alone or beside a crosswalk cell without a recognized opening verb is not flagged; the candidate title is captured to the field boundary (including closing wrappers `**`, `__`, backtick, `*`, `_`, and every accepted punctuation separator, except word-internal hyphens, slashes, en/em dashes, parentheses, brackets, asterisks, underscores, backticks and apostrophes; compounds joined by any word-internal mark count by their parts for the two-word minimum, preserving their spelling; for a single-quoted candidate the last closing quote before the next non-quote field boundary closes the title; a double-quoted candidate ends at the first closing double quote; apostrophes inside double quotes remain part of the title; in an unquoted candidate, a plural possessive (`s'` or `S'` followed by whitespace and a capitalized word) also continues the title), capped at 8 words, and compared case-insensitively (whitespace-normalized) to the canonical. Residual: a wrong title opening with a word outside the listed forms, or with no verb at all (for example, `MEA03, External Compliance`), is not detected. Separators or wrappers outside the accepted set (for example `**MEA03:** Title`, italic or curly-quoted titles, a linked code, or stacked separators) are also not detected. Added forms in other cases and single-word candidates are intentionally outside this precision-first check. Known false positives include sentence-case prose after a code (for example, `APO12: Assessing risk is required annually`), a canonical title used as a plural possessive before a capitalized word (for example, `APO10 Managed Vendors' SLAs`), `BAI03 Built-in controls apply`, and `per APO12 - Managed risk-based approach`. An unspaced em dash followed by a word continues a title, so MEA03 with its canonical title followed by an unspaced em dash and `anchors this` is flagged; prose em and en dashes are both forbidden by the language gate. An unspaced en dash after a spaced en-dash separator also continues the title, so the code APO12, a spaced en dash, then its canonical title joined to further words by an unspaced en dash (for example, `ISO 31000 crosswalk`) is a known false positive. It shares gate 61's scan scope (`iter_markdown_targets` with `DEFAULT_EXEMPT_DIRS`, so `.working` and `.claude` are out and `.project-governance` is in, and the shared `EXEMPT_FILES`). Gate 78 is a Backlog item-number permanence audit (PR #1173): backlog item numbers are permanent and are never recycled, so a closed number retires with its item and every edit advances its section's `Next item number` counter. The rule was adopted 2026-07-15 and had no mechanical enforcement, and it was broken twice before this gate, once with a live consequence: a recycled number sent held research to the wrong item. Live ids come from index rows in both backlog files, `### <id>` headings in the private file, and, since 3b120, top-level bold-bullet items in both, read by the backlog-actionability tool's own parser; retired ids come from `DONE.md` headings in three conventions: the section-marked `§N.M` form, the private `P-N.M` form, and the queue `3bNN` form, which is read only from two structured positions (the id list right after the `PR #N:` or date prefix, optionally led by a repository word such as `grc_library_ref PR #156:`, and a parenthetical of ids just before the trailing date), because a queue id anywhere else in a heading is a mention and a list of mention words cannot be complete. In the lead position a following parenthetical or a partial word (part, partial, phase, slice, split) keeps the item open; other partial wording retires the id and turns the gate red, which an `EXEMPT` row clears. A false retirement is therefore always loud, while a missed closure is silent: a closure recorded only as a mention, with a lead parenthetical, in a heading that omits its id, or in any other heading shape outside the two positions (the design note in the tool gives examples) is not read. An open backlog item makes the finalize tooling write the closed id in the lead position, which is the durable fix. An unclosed code fence or HTML comment in either backlog file is also reported, because it hides every later bullet item from the live set. The gate reports four classes: a number denoting both a live item and a recorded retirement; a section counter at or below the highest ordinal used in its section (live, retired, or the highest ordinal ever allocated for that section per the public number floor `tools/todo-number-floor.json`); a number that is live in both `TODO.md` and the private `P-TODO.md` at once, which is a botched migration that copied an item instead of moving it; and, since 3b120, the unclosed fence or comment described above. Its false-positive surface is deliberately NOT the parse but the completeness of its `EXEMPT` dict, because the parse cannot distinguish a partial close, or the close of one sub-item, from a full retirement; every legitimate live-and-retired coexistence is therefore enumerated there with its reason, and a future partial close adds its row in the same change that records the close. `EXEMPT` is keyed by a distinctive `DONE.md` heading SUBSTRING rather than a line number, because a line key was measured to lapse whenever an unrelated change shifted the file. It carries two classes: a closed set of pre-rule grandfathers, where a number was reassigned before the rule existed and which cannot be fixed forward because the same rule forbids renumbering an existing item, and partial closes against still-open umbrella items. Gate 109 is an isolated-launch import audit: [`tools/lint-isolated-launch.py`](../tools/lint-isolated-launch.py) prepares the toolchain for running every gate under `python3 -I`. Isolated mode leaves the script's own directory off `sys.path`, so a file planted beside a tool cannot shadow a standard-library module, and so a tool that imports a `tools/` sibling module without placing its own directory on the path fails on that import. The conversion appends each tool's resolved directory to the end of `sys.path`, after the standard library and site-packages and never at index 0, and [`tools/aiqt_bootstrap.py`](../tools/aiqt_bootstrap.py) appends the AIQT pack's `tools/` directory the same way, moves an entry for it that a caller already placed earlier on `sys.path` to the end, and refuses with `ImportError` when `aiqt_corpus` then resolves, or was already imported, from anywhere but the located pack's `tools/aiqt_corpus.py` (an installed copy in site-packages would otherwise outrank the appended pack). The gate checks module-level imports, not a full command launch, and says so in its output. For every `tools/*.py` the gate starts a child `python3 -I -B` that installs an audit hook and then runs the tool's module-level code under a module name other than `__main__`, so the tool's imports run and its entry point does not. The hook refuses the audited events listed in the gate: the process starts `subprocess.Popen`, `_posixsubprocess.fork_exec`, `os.system`, `os.exec*`, `os.spawn*`, `os.posix_spawn*` and `os.fork`; an `open` for writing and the listed file-system changes; outbound sockets (`socket.connect`, `socket.bind`, `socket.sendto` and `socket.sendmsg`; a name lookup is not refused); signals; every `ctypes.*` event (`ctypes.dlopen`, which `import ctypes` itself raises, `ctypes.dlsym` and `ctypes.call_function` among them); and every `sqlite3.*` event (`sqlite3.connect` and the extension loads). Reads are allowed. A finder placed last on `sys.meta_path` records each top-level import of a `tools/` sibling that no other finder resolved, so a sibling import the tool catches and ignores still counts. Each tool's outcome is `ok`, `sibling` (a sibling import failed, and any exception raised was that sibling's own `ImportError`) or `error` (any other exception, `SystemExit` included, whether or not a sibling was also missed, so the probe cannot show that its imports complete). Separately, the gate reads each tool's source for a `sys.path.insert(...)` call at any index, a `sys.path.__setitem__`, `__iadd__`, `sort` or `reverse` call, an assignment or augmented assignment (`+=`) to `sys.path` or to an item or slice of it, or a rebinding of `sys.path`, anywhere in the file; each can put the tool's own directory or the corpus-management pack's `.corpus-management/tools` ahead of the standard library. The check is static because most of these inserts run inside a function, which the module-level probe never reaches. The tools whose sibling import fails are listed on the gate's `BASELINE`, which held 100 of the 198 `tools/*.py` files when the gate landed; the tools that insert into or assign `sys.path` are listed on its `INSERT_BASELINE`, which held 98 when the list was added (`tools/preflight_language_runner.py` was converted to the append form at the same time). Delta gates D1, D2, D3, D4, D7, D11 and D15 resolve the pull request range with one shared resolver ([`lint_common.resolve_pr_range`](../tools/lint_common.py)), and each compares the head with a single merge base. Delta gate D4 enforces the Version-Date co-bump half of the version-bump discipline: when a PR bumps a versioned document's `**Version:**` field, the same change must set that document's `**Date:**` field to the date its Version-bumping commit was made (UTC). Its narrative-content scope is `executive/*.md` minus the top-level `README.md` entry point, path-scoped so a nested `executive/sub/README.md` is still content; the changed-file enumeration uses `--no-renames -z` so a boundary-crossing rename shows both sides and a quoted path classifies correctly. It has zero false-positive surface while `executive/` holds no authored content pages. The interim posture is fail-closed with no override path: the specification's accountably-reviewed override marker (never mere presence) is a governance-design obligation reserved to the maintainer, and a fail-closed interim is stricter than the specified end state rather than looser, so it is faithful to the boundary.

Delta gate D12 is the number-floor monotonicity check ([`tools/check-todo-floor-monotonic-on-pr.py`](../tools/check-todo-floor-monotonic-on-pr.py)): it compares [`tools/todo-number-floor.json`](../tools/todo-number-floor.json) (the public floor gate 91 generates the `## Number allocation` counters from, and gate 78 reads for its recycle check) against the PR's merge base and FAILS if any series' floor DECREASED or a series was dropped. The floor records the highest ordinal EVER allocated per series and may only rise (a new allocation) or stay put; a hand-edit that lowered it would rewind a counter and silently permit recycling a retired id, which the at-rest gates 91/78 (each enforcing only that a counter is not BELOW the floor) cannot see because the floor is its own only witness. D12 closes that pull-request seam, so the number-permanence guarantee terminates in machinery in both the omission direction (gates 91/78) and the decrease direction (D12), not in human discipline. The comparison point is the merge base, not the base itself, so a floor the base raised after the branch forked is not read as the branch lowering it; when a criss-cross history gives the PR more than one merge base, D12 compares the head floor with the floor at each merge base that has one and FAILS on a decrease against any of them. When no merge base has the floor and the head does, the PR introduces it: D12 still reads the head floor and validates it as a floor document, and refuses (exit 2) when it cannot be read or is not a floor document, so only a valid introduced floor passes, with nothing prior to compare.

Delta gate D13 is the stranded-control-code check ([`tools/check-stranded-control-code-on-pr.py`](../tools/check-stranded-control-code-on-pr.py)): it is the diff-scoped tripwire for the paired-surface stranding class, where a PR corrects a control code in a document's framework-alignment TABLE but leaves the same document's inline BODY prose citing the OLD code. Such a stranded cite is still a well-formed, in-catalogue citation, so no existence gate (the citation and control-code gates) can see it; only a same-document, delta-scoped check catches it. It diffs each changed corpus document against the merge base, takes the set of control codes REMOVED from table lines (expanding `X-N to M` ranges first, so a range-to-single edit differs correctly), drops any code still present in a table row at HEAD (a body cite anchored to an unchanged row stays consistent), and scans the document's non-table lines for each survivor with an anchored matcher (an enhancement notation such as `SA-11(8)` is a deliberate narrower cite and never counts as a survivor of `SA-11`). A hit FAILS unless the PR carries a non-empty `StrandedCode: <reason>` commit trailer for a legitimate residue. The central compliance matrix is out of scope (its cross-document consistency is the `/matrix-fit` cadence's concern). Measured false-positive rate zero over the prior 80 commits; it is deletion-triggered and same-document only, a defence-in-depth layer under the multi-family QA that catches this class only sometimes.

Delta gate D14 enforces the class-completeness attestation on the open-findings ledger (PR #1989, the mechanization of the fix-at-class-width discipline whose reactive shape was the recurring "fix the cited instance, miss the siblings" class). The ledger is maintainer working state resolved through the shared working-state helper, so on a clone where no ledger resolves (public CI, an adopter checkout) the gate has nothing to check and exits zero; its fail-closed property binds where the ledger exists, the maintainer's pre-push runner. For each `## Open` or `## Closed today` row whose Found date is on or after the gate's ship-date floor (a dynamic floor: pre-mechanization rows are never retro-failed), whose disposition is a valid `FIXED` with an adjacent reference, and whose Finding cell leads with a bracketed class token, the gate requires either a `[class: "<token>" @ <count>]` attestation or a `[class-exempt: <reason>]` clause with a reason from the closed set (`singleton`, `non-textual`, `cross-repo`), and for the former it reproduces the completeness probe: it re-runs the shared class-completeness matcher for the attested token over the git-tracked corpus markdown set and fails when the occurrence count exceeds the attested count (a sibling survived, or a new instance crept in while the row sat open) or when any corpus file is unreadable (the probe cannot cover the set). The activation floor is the day AFTER the gate merges rather than the merge date, because the ledger's day-granular Found cell cannot distinguish a pre-grammar row authored on the merge day from a post-grammar one; the deliberate, self-closing residue is that a class finding both added and fixed-without-attestation on the merge day itself is exempt (bounded by the hours to 00:00 UTC, and, while the row remains in `## Open`, still drawn to the open-findings hook's advisory warning, though that advisory does not fire once the row is moved to `## Closed today`), which the retroactive attestation of the pre-grammar rows later closes. The gate re-runs the declared probe and never re-judges relatedness: the token and count are author-declared through the class-completeness aid's `--attest` mode, because the finding prose has no authority to answer which distinctive string identifies the class. The gate scans both `## Open` and `## Closed today` (a fixed finding is dispositioned and moved to `## Closed today` in the same PR, so an Open-only scan would miss the very rows it verifies); the dynamic ship-date floor plus the eventual archiving of the `## Closed today` bucket keep a legitimately growing token from failing pushes indefinitely, and growth while a row is still in the current ledger requires an explicit re-attestation, which is the class re-check working rather than a false positive. The open-findings PreToolUse hook surfaces the same missing-attestation condition as a fail-open warning at PR create and merge time; this gate is the fail-closed half of that pair. Delta gate D14 also fails closed on a MIS-FILED finding-row (PR #1996): a `date | severity |`-leading, column-0, non-fenced row that appears BEFORE the `## Closed today` archive opens (in the preamble above `## Open`, or orphaned between `## Open` and `## Closed today` by a phantom heading) is invisible to both the hook and this gate (the observed 2026-09-05 corruption spliced twelve dispositioned rows into the `## Disposition values` legend, with a false backtick-quoted `## Closed today` heading). The detector shares the parser's heading AND delimiter-aware code-fence semantics (a backtick-bearing or fenced `## ` line no longer opens a scanned section for either, closing the phantom-heading and fenced-heading seams) and stops once the real `## Closed today` opens, because the ledger keeps a legitimate archive of old finding-rows under dated `## YYYY-MM-DD` headings below `## Closed today` in the same row schema; the stated residues (an undispositioned row spliced into the archive, and a row fused onto a prose line) are recorded at the detector.

Delta gate D15 is the advisory alignment-citation register check ([`tools/check-alignment-register-on-pr.py`](../tools/check-alignment-register-on-pr.py)): it WARNS when a pull request adds a citation of a standard or regulation that has no row in the canonical-citations register ([`register-canonical-citations.md`](register-canonical-citations.md)), the register's own "add an entry here before the citing PR merges" maintenance rule, which nothing enforced (the 2026-10-04 PR #2697 cited the Critical Entities Resilience Directive and the Commission Recommendation defining micro, small and medium-sized enterprises by instrument number in prose, with no row for either). It reads only the lines the PR adds or changes in Markdown documents under the audited domain directories (taken from `lint_common.AUDITED_DOMAIN_DIRS`, minus gate 6's exempt files), and four surfaces on those lines: the first cell of a row in a list-form alignment table (a table whose first header cell, such as `Framework` or `Regulation`, means that each row names one framework or standard); the header cells of a matrix-form alignment table under a framework-alignment or crosswalk heading, when the PR adds the header row; each segment of a free-text citation-list column (`Regulatory`, `Legal / Regulatory`, `Other` and similar) once its provision suffix is removed; and any EU/EC instrument number on an added non-code line, compared by number with the numbers in the register's Standard ID, Current version and Superseded versions cells. It imports gate 6's register parser and identity normalization rather than keeping its own: a citation inside gate 6's grammar is reported only when gate 6's own resolver finds no row (`UNREGISTERED`), so the two tools cannot read the same row differently; any other citation is registered when, without its trailing edition, it matches a Standard ID exactly, through a curated alias or umbrella pattern in [`tools/alignment-register-aliases.json`](../tools/alignment-register-aliases.json), as a whole-word suffix or series prefix of a Standard ID, or through an EDPB or Article 29 Working Party designator. The exclusion policy is data, [`tools/alignment-register-exclusions.json`](../tools/alignment-register-exclusions.json), which encodes the maintainer decision of 2026-10-16 ("Tracked only"): the register covers standards and regulations whose currency is tracked, so an unregistered RFC, vendor guidance or book is not reported; each policy pattern or entry names its class and its reason, and the file is validated on load. The remaining heuristic skips generic placeholders, column labels, bare publisher names, control-code fragments, bare number fragments, lowercase prose without an instrument word or number, and segments with no acronym or digit, and no instrument word in a multiword name; digit-leading CFR citations and lowercase instrument names remain citable. Once its modules load, the check always exits zero, the D8 precedent, and it is deliberately absent from [`tools/run_all_audits.sh`](../tools/run_all_audits.sh): that runner hides a passing gate's warnings, and a corpus gate must carry a near-zero false-positive rate, which an alias-dependent name match cannot promise. D15 reads the register at `--register-ref` when it is given and at the head otherwise. A register that is absent there (an adopter may drop it) or cannot be read ends the run, and so does a changed document in scope whose diff or head content cannot be read. Each of these, a missing merge base or more than one, and a failed `git diff` of the changed file names ends the run before the sibling probe described below, with only its own printed note and no note that the probe was skipped. A head without the register does not end a run with a `--register-ref` that has one: the main check reads that ref's register, and the probe compares the head's absent register as one with no rows, so when the pull request deletes the register every Standard ID of the merge base's register counts as removed. An unreadable policy file is a printed note and a no-op for the main check; the sibling probe still lists siblings then only when the file that failed is the alias file in the checkout (absent, unreadable or malformed), which the probe does not read; it also needs the exclusion policy in the checkout, a register that parses, and a head alias file that is absent or loads, and it prints a note that it was skipped when one of them fails. Replayed with D15 and the register as shipped, the 120 first-parent commits ending at 4a921daf produced 33 added-citation warnings in 12 commits (including the PR #2697 lines); the final 20 of those commits produced none; these advisory warnings require review and do not by themselves establish that a register row is missing. It is delta-only and recognizes only those four surfaces, so an instrument named in prose without a number, or a citation already on `main`, is outside its reach (gate 6's report mode inventories the latter for its grammar families). When the pull request changes the alias file or the register, the same run adds a report-only sibling probe with no gate number of its own: it scans the three alignment-table surfaces across the whole corpus at the pull request head and prints a `D15 SIBLING` line for each citation that is still unregistered and shares a distinctive token with an alias key that the pull request adds, removes or retargets, or with a register Standard ID that it adds or removes, so that another form of the same instrument, or a related instrument, can be found in the same round (in PR #2833, backlog 3b364, round 1 aliased `US TSA Pipeline Security Directives` while the related sibling row `US TSA Rail Cybersecurity Directives`, a separate TSA directive set, kept warning until a later round). The probe compares only the set of Standard IDs: a row whose Standard ID is edited counts as the old ID removed and the new one added, and an edit to a row's other cells (a date or a version) changes nothing, so on 2026-10-17 a synthetic edit that moved every date in the `Last verified (UTC)` cells of all 23 register tables one day later listed nothing. That edit changed 217 dates in 216 of the 219 rows of those tables: 189 of the 192 Standard ID rows, and the 27 rows of the AI security tooling references table, which is keyed by `Project` and which gate 6 does not parse; the other 3 rows read `needs-reconfirm`. Taking each of those 189 Standard IDs as changed lists 86 citations. The probe resolves citations with the head's alias file, and treats an absent one as an empty map; the main D15 check reads the alias file in the checkout, which in CI is the commit checked out as the head (the pull request merge ref), and both read the exclusion policy in the checkout. With `--register-ref`, the family tokens and the judgement of which citations are unregistered use that ref's register. A distinctive token is a designator mixing letters and digits, a number of three or more digits that is not a year, or a word of three or more letters outside a stop list of function words, words that name a kind of instrument, a topic or a jurisdiction, and generic words that paired unrelated instruments of different publishers (`party`, `assessment`, `access`, `design`, `provisions`, `certification` and others); accents are removed first (NFKD, combining marks dropped), so the accented and unaccented spellings of `Quebec` match. In every case the token must also appear in fewer than ten register Standard IDs (on 2026-10-17, `ISO`, `IEC`, `NIST`, `800` and `Canada` name families of rows and are not distinctive). The probe lists in two tiers so that a citation sharing only a distinctive word is still listed and the noise stays visibly weak. A citation that shares a changed entry's acronym (a word with a capital after its first letter, such as `TSA`, `MiCA` or `GenAI`), designator or number is a `D15 SIBLING` line. A citation that shares no acronym, designator or number with any changed entry and a distinctive word with at least one is a `D15 SIBLING (word match)` line, printed after the strong lines with the shared words named. For example, the spelled-out `Transportation Security Administration Pipeline Security Directives (SD Pipeline-2021-02G)` shares only `pipeline` with the former alias key `US TSA Pipeline Security Directives` (removed in PR #2839; a test adds it back as a fixture); the 3b370 round 2 review found it lost when an entry with an acronym was matched on its acronym alone. A word match is weak evidence and is often a different instrument. A NOTE line names each changed entry with no distinctive token, and any change to the alias file's `umbrella` or `not_citable` entries, which the probe does not compare. The probe never changes the exit status. Its residual is printed beside its result. Not listed are: a form that shares no distinctive token with the changed entry (`Law 25` beside `Quebec Law 25`, or a spelled-out name beside its acronym that shares no distinctive word with it, such as one sharing only stop words or family tokens: `Cloud Security Alliance Cloud Controls Matrix v4.1` beside `CSA Cloud Controls Matrix`); every form of a changed entry with no distinctive token; a form sharing only a family token (the family tokens of the register in use are printed); a sibling outside the three alignment-table surfaces (prose, an EU/EC number or another table); and the siblings of an `umbrella` or `not_citable` change. A listed citation can also be a different instrument from the same publisher.

## 7. Phase-completion gating

A phase is complete when:

1. All file edits intended for the phase are written.
2. Auto-generated artefacts ([`taxonomy.yml`](../taxonomy.yml), [`narrative.yml`](../narrative.yml), [`docs/portal.md`](../docs/portal.md), [`docs/maturity-scorecard.md`](../docs/maturity-scorecard.md), [`governance/relationship-model.generated.json`](relationship-model.generated.json), and the generated `## Number allocation` block in [`TODO.md`](../TODO.md)) have been regenerated.
3. The full audit programme passes locally via [`tools/run_all_audits.sh`](../tools/run_all_audits.sh).
4. The CHANGELOG entry for the phase is written.
5. The library calendar version is bumped (and the README version where appropriate).
6. The change is committed and pushed; the pull request is opened.
7. CI's quality.yml workflow confirms green.
8. The pull request is merged and the local branch is fast-forwarded to the merged main.

Selective subset runs are not a substitute for the full sweep. This rule was established (per a closed backlog lessons-learned decision) after a phase-bundle merge introduced five gate violations that would have been caught by a full local sweep.

## 8. Audit programme failure handling

When an audit gate fails, the maintainer (or AI verifier) must:

1. **Read the failure message in full.** Each gate prints the offending file, line, and content.
2. **Locate the underlying cause.** Do not edit the linter to suppress the finding without first investigating whether the linter is correct.
3. **Choose between three responses:**
    1. **Fix the content.** This is the default response. The content is in violation of a documented rule; the content is corrected.
    2. **Extend the linter's exemption list.** Only when the content is correct and the rule does not apply (e.g., the [`tools/lint-citations.py`](../tools/lint-citations.py) `COBIT 2025` exemption granted to documents that *deliberately* discuss the hallucinated framework version as a warning). The exemption must name the file by relative posix path and is recorded inline next to the existing exemption set.
    3. **Modify the rule.** Only when the rule itself is wrong (e.g., the Phase 23.20 loosening of [`lint-required-sections.py`](../tools/lint-required-sections.py) to accept Purpose OR Scope OR Applicability OR Introduction OR Overview). Rule modifications require an entry in the CHANGELOG and a corresponding update to the linter's module docstring.

Bypassing a hook (`--no-verify`, `--no-gpg-sign`, etc.) is not a permitted response. If a hook fails, the underlying defect is fixed before commit, not bypassed.

## 9. Adding a new gate

A new gate is added when:

1. A class of defect is identified that current gates do not catch.
2. The defect is deterministically detectable from repository state without network access or third-party dependencies.
3. The signal-to-noise ratio of the proposed rule is acceptable (false-positive rate is empirically zero or near-zero on the current corpus).

The procedure for adding a gate:

1. Write the linter as `tools/lint-<feature>.py` (Python 3.11, stdlib only).
2. Confirm the linter exits 0 on the current corpus (zero false positives).
3. Add the gate to [`.github/workflows/quality.yml`](../.github/workflows/quality.yml), [`tools/run_all_audits.sh`](../tools/run_all_audits.sh), [`.pre-commit-config.yaml`](../.pre-commit-config.yaml), and the §6 inventory table above.
4. Add the new gate's row to the §6 inventory; §5 places the gate in its functional category. The §6 inventory table is the canonical source of truth for the gate count.
5. Record the addition in the CHANGELOG under a new phase entry.

## 10. Modifying or retiring a gate

A gate is modified when its rule is found to be incorrect (Phase 23.20 pattern). The modification must include:

1. The corrected linter code.
2. A re-run of the full audit sweep to confirm no new violations surface.
3. A CHANGELOG entry naming the gate, the rule that changed, and the rationale.
4. An update to the linter's module docstring if the rule's substance changed.

A gate is retired when its rule is found to be unhelpful, dominated by another gate, or producing structural false positives that cannot be narrowed. Retirement requires a documented rationale (per a closed backlog decision, following the Strict-Related-Documents-Reciprocity precedent).

## 11. Relationship to the Citation Verification Specification

The Audit Programme Specification and [`governance/specification-citation-verification.md`](specification-citation-verification.md) form a complementary pair:

| Concern | Governed by |
| --- | --- |
| Are the library's internal references, structure, naming, metadata, and language internally consistent? | Audit Programme Specification (this document) |
| Are the library's claims about external standards accurate against publisher canonical sources? | Citation Verification Specification |

Three of the gates sit at the boundary between the two programmes:

- [`tools/lint-citations.py`](../tools/lint-citations.py) (gate 5) detects literal-string drift on external framework versions (for example, the canonical "COBIT 2025" hallucination warning). Its substance is a claim about the world (what version of COBIT is current), which derives from the Citation Verification Specification; its mechanism is deterministic repository-state pattern matching, which is the audit programme.
- [`tools/lint-citation-verification-freshness.py`](../tools/lint-citation-verification-freshness.py) (gate 27) and [`tools/lint-tooling-provenance-freshness.py`](../tools/lint-tooling-provenance-freshness.py) (gate 28) enforce the freshness cadences (12-month for canonical citations, 6-month for active tooling, 12-month for archived tooling) defined in Citation Verification Specification §12.

These three gates are determined automatically from repository state (so they belong to this programme) but enforce semantics defined in the Citation Verification Specification (so their substance derives from there).

When the two specifications conflict, the Citation Verification Specification governs the *substance* of what counts as "verified" and "fresh"; this specification governs the *enforcement mechanism* by which that substance is checked at every change.

## 12. Out-of-scope acknowledgements

The audit programme does not, and cannot, detect:

- **Substantive correctness of content.** A linter cannot detect that a paragraph asserts something untrue about the world; that is the domain of human review and (for external claims) the Citation Verification Specification.
- **Architectural coherence.** Whether a new document is well-placed in the library's information architecture is a human judgement, not a machine-detectable property.
- **Semantic duplication.** Two documents that say the same thing in different words pass every gate; identifying such duplication is part of the manual review cadence.
- **Adopter usefulness.** Whether a document is actually useful to a downstream adopter is not testable from repository state alone.

These limitations are not defects in the audit programme; they are the natural boundary at which automated quality gates stop and human judgement begins. The audit programme is a necessary but not sufficient condition for library quality.

## 13. Framework alignment

The audit programme contributes to control objectives in the following frameworks (cross-referenced for adopter convenience, not authoritative attribution):

- **ISO/IEC 27001:2022 Annex A.5.36 (Compliance with policies, rules and standards for information security)**: automated regular review of governance artefacts' compliance with the library's documented rules.
- **NIST CSF 2.0 GV.OC (organizational context)**: documented internal consistency mechanisms.
- **COBIT 2019 BAI06 (Managed IT Changes)**: pre-commit and pre-merge gating preventing unreviewed changes.
- **NIST SSDF: N/A**: the pre-commit hooks and CI enforcement of repository quality are documentation-quality automation, not secure development tooling.

These mappings illustrate where automated audit-programme work touches recognized frameworks; they do not claim equivalence.
